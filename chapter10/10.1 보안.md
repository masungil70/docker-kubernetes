
### 보안

  개념 이해: 인증 vs 인가

  먼저 두 가지 개념을 명확히 구분해야 합니다.

   1. 인증 (Authentication): "당신은 누구입니까?"
       * API 서버에 요청을 보낸 주체(사용자, 시스템)가 누구인지 신원을 확인하는 과정입니다.
       * 예: 로그인 절차와 같습니다. 아이디/비밀번호, 인증서, API 키 등을 통해 신원을 증명합니다.

   2. 인가 (Authorization): "무엇을 할 수 있습니까?"
       * 인증된 사용자가 특정 리소스(예: 파드, 디플로이먼트)에 대해 어떤 작업(예: 생성, 조회, 삭제)을 수행할 권한이 있는지 결정하는 과정입니다.
       * 예: 로그인 후, 일반 사용자는 글을 읽을 수만 있지만 관리자는 글을 쓰고 지울 수도 있는 것과 같습니다.

  Kubernetes의 모든 API 요청은 반드시 인증 -> 인가 순서의 단계를 거칩니다.

  ---

  1단계: 인증 (Authentication) 전략

  Kubernetes는 자체적으로 사용자 정보를 관리하지 않습니다. 대신 다양한 인증 방식을 플러그인처럼
  지원하며, 관리자는 이 중에서 선택하여 구성해야 합니다.

  주요 인증 방식

   1. X.509 클라이언트 인증서 (가장 일반적)
       * kubectl이 API 서버와 통신할 때 기본적으로 사용하는 방식입니다.
       * 인증서는 CN(Common Name)을 사용자 이름으로, O(Organization)를 그룹으로 사용합니다.
       * 클러스터 관리자가 사용자를 위해 개인 키와 서명된 인증서를 생성하여 kubeconfig 파일 형태로
         전달합니다.

   2. 서비스 어카운트 (Service Accounts)
       * 파드(Pod) 안의 프로세스가 API 서버와 통신할 때 사용하는 "기계용" ID입니다.
       * 네임스페이스에 종속되며, 파드가 생성될 때 자동으로 해당 네임스페이스의 default 서비스
         어카운트 토큰이 파드 내부에 마운트됩니다
         (/var/run/secrets/kubernetes.io/serviceaccount/token).

   3. OIDC (OpenID Connect) 토큰
       * Google, Okta, Keycloak 같은 외부 ID 공급자(Identity Provider)와 연동하는 방식입니다.
       * 사용자는 기존에 사용하던 회사 계정 등으로 로그인하고, ID 공급자가 발급한 JWT(JSON Web
         Token)를 사용하여 API 서버에 인증합니다. 주로 엔터프라이즈 환경에서 사용됩니다.

   4. 정적 토큰/비밀번호 파일
       * 단순한 CSV 파일에 토큰,사용자,UID 형식으로 사용자 정보를 저장하는 방식입니다. 간단하지만
         보안에 취약하고 동적으로 관리하기 어려워 거의 사용되지 않습니다.

  ---

  2단계: 인가 (Authorization) 전략

  인증을 통해 신원이 확인되면, 해당 사용자가 요청한 작업을 수행할 권한이 있는지 검사합니다.
  Kubernetes에서는 주로 RBAC(Role-Based Access Control) 방식을 사용합니다.

  RBAC의 핵심 구성 요소

  RBAC는 4가지 주요 리소스로 구성됩니다.

   1. Role (역할)
       * 특정 네임스페이스 내에서 리소스에 대한 권한(허용되는 동사: get, list, watch, create, update, delete 등)을 정의합니다.
       * 예: development 네임스페이스 안의 pods를 get, list 할 수 있는 권한.

   2. ClusterRole (클러스터 역할)
       * 클러스터 전체 범위의 권한을 정의합니다.
       * 용도:
           * nodes, persistentvolumes처럼 네임스페이스에 속하지 않는 클러스터 자원에 대한 권한.
           * 모든 네임스페이스에 걸쳐 동일한 권한을 부여할 때 (예: 모든 네임스페이스의 pods 조회).

   3. RoleBinding (역할 바인딩)
       * Role을 특정 사용자(User), 그룹(Group), 또는 서비스 어카운트(ServiceAccount)에 연결합니다.
       * 네임스페이스 범위에서만 유효합니다. 즉, RoleBinding이 존재하는 네임스페이스에서만 권한이 적용됩니다.

   4. ClusterRoleBinding (클러스터 역할 바인딩)
       * ClusterRole을 클러스터 전체 범위에서 특정 주체에게 연결합니다.
```
  > 핵심 관계:
  >    Who?* -> User, Group, ServiceAccount (주체, Subject)
  >    What?* -> Role, ClusterRole (권한 정의)
  >    Connection* -> RoleBinding, ClusterRoleBinding (주체와 권한 연결)
```

  예제 1

  목표: dev-user라는 새로운 개발자에게 development 네임스페이스의 파드(Pod)를 조회만 할 수 있는 권한을 부여해 보겠습니다.

  사전 준비

  먼저, 예제에서 사용할 폴더를 생성합니다 

```
mkdir step1 && cd step1
```  

폴더 구조 
```
step1
├── dev-user-binding.yaml
└── pod-reader-role.yaml
```

예제에서 사용할 네임스페이스를 생성합니다.

```
kubectl create namespace development 
```

✦ 1. 인증: 사용자 생성 (개념)

  실제 환경에서는 클러스터 관리자가 openssl 같은 도구를 사용해 dev-user를 위한 X.509 인증서를 생성합니다. 이 인증서의 CN(Common Name)은 dev-user가 됩니다.
  kubectl은 이 인증서가 포함된 kubeconfig 파일을 사용하여 API 서버에 자신을 dev-user라고 알립니다. 

  2. 인가: RBAC 규칙 생성

  이제 dev-user에게 필요한 권한을 RBAC 리소스를 통해 정의하고 연결합니다.

  A. Role 생성: 파드 조회 권한 정의

  development 네임스페이스에서 파드를 get, list, watch 할 수 있는 pod-reader라는 이름의 Role을 만듭니다.
```
vi pod-reader-role.yaml

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: development
  name: pod-reader
rules:
- apiGroups: [""] # ""는 핵심(core) API그룹을 의미합니다.
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
```

  이 파일을 클러스터에 적용합니다.

```
  kubectl apply -f pod-reader-role.yaml 
```
  생성된 role을 확인 합니다 
```
kubectl get role -n development
kubectl describe role -n development
```

✦ B. RoleBinding 생성: 사용자와 Role 연결

  이제 dev-user를 위에서 만든 pod-reader Role에 연결합니다. 이 연결은 development 네임스페이스에서만 유효합니다.

```
vi dev-user-binding.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-in-development
  namespace: development
subjects:
- kind: User
  name: dev-user # 인증서의 CN 값과 일치해야 합니다.
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader # 위에서 생성한 Role의 이름
  apiGroup: rbac.authorization.k8s.io
```

  이 파일도 클러스터에 적용합니다.
```
kubectl apply -f dev-user-binding.yaml
```
  생성된 RoleBindings을 확인 합니다 
```
#생략형
kubectl get rolebindings -n development
#풀네임
kubectl get rolebindings.rbac.authorization.k8s.io -n development
#상세정보 확인합니다 
kubectl describe rolebindings -n development
```

✦ 3. 검증

  이제 dev-user의 권한을 확인해 볼 차례입니다. kubectl의 auth can-i 명령어를 사용하면 특정 사용자를 가정하여 권한을 테스트할 수 있습니다.

  성공하는 경우 (허용된 작업):
  dev-user가 development 네임스페이스의 파드를 조회할 수 있는지 확인합니다.

```
kubectl auth can-i list pods --namespace development --as dev-user
#또는 
kubectl auth can-i list pods -n development --as dev-user
kubectl auth can-i list pods --as dev-user -n development 

```

✦ 결과가 yes로 나옵니다. 권한이 성공적으로 부여되었습니다.

  실패하는 경우 (허용되지 않은 작업):
  dev-user가 파드를 삭제하려고 시도하면 어떻게 될까요?
```
kubectl auth can-i delete pods --namespace development --as dev-user
```
✦ 결과가 no로 나옵니다. pod-reader Role에 delete 동사가 없기 때문입니다.

  다른 네임스페이스에 접근하는 경우:
  dev-user가 default 네임스페이스의 파드를 조회하려고 하면 어떻게 될까요?

```
kubectl auth can-i list pods --namespace default --as dev-user
```

✦ 결과가 no로 나옵니다. RoleBinding이 development 네임스페이스에만 존재하기 때문입니다.

  정리

   * 1단계 (인증): 클러스터에 접근하는 주체의 신원을 확인합니다. (예: kubeconfig의 인증서로 dev-user 식별)
   * 2단계 (인가): RBAC 규칙에 따라 해당 주체가 요청한 작업을 할 수 있는지 확인합니다.
       * Role은 "무엇을 할 수 있는지"를 정의합니다. (파드 조회)
       * RoleBinding은 "누가" 그 역할을 할 수 있는지 "어디서" 할 수 있는지 연결합니다. (dev-user가 development 네임스페이스에서)
   * 이 두 가지 메커니즘을 통해 Kubernetes는 멀티테넌시와 최소 권한 원칙(Principle of Least Privilege)을 구현하여 클러스터를 안전하게 보호합니다.

생성된 모든 리소스를 삭제합니다 
네임스페이스를 삭제하면 네임스페이스에 속한 모든 리소스가 삭제됩니다. 
```
kubectl delete namespace development
```

  예제 2

  목표:  RBAC 설정을 기반으로, X.509 인증서를 생성하여 dev-user 사용자를 인증하고 권한을 테스트하는 전체 과정 알아 보겠습니다. step2의 dev-user는 development 네임스페이스에서 파드를 읽을 수 있는 권한만 가집니다. 파드, 디플로이먼트, 서비스를 직접 생성할 수는 없습니다.
  따라서 먼저 관리자 권한으로 예제 리소스를 생성한 다음, dev-user 계정으로 해당 리소스에 접근하여 권한을 테스트하는 방법으로 진행합니다

```
#이전에 작성한 파일을 복사 해 옵니다 
cp ../step1/* .
```

k8s의 핵심 구성관리자 권한, 별도의 작업이 없으면 기본입니다 

```

```



[단계 1] RBAC Role 및 RoleBinding 적용 
step1에서 정의한 pod-reader Role과 dev-user를 위한 RoleBinding을 클러스터에 적용합니다. 
```
#폴더 변경합니다 
cd ../dev-user

kubectl apply -f pod-reader-role.yaml
kubectl apply -f dev-user-binding.yaml
```

[단계 2] 사용자 개인 키 생성 
dev-user 사용자의 2048비트 RSA 개인 키를 생성합니다. (dev-user.key)
```
openssl genrsa -out dev-user.key 2048

#생성된 개인 키 확인합니다
cat dev-user.key
```

[단계 3] 인증서 서명 요청(CSR) 생성 
개인 키를 사용하여 CSR을 생성합니다.
CSR의 CN(Common Name)은 사용자 이름을 나타냅니다.
```
openssl req -new -key dev-user.key -out dev-user.csr -subj "/CN=dev-user"

#인증서 서명 요청을 확인합니다
cat dev-user.csr
```

[단계 4] 쿠버네티스 CertificateSigningRequest 오브젝트에서 사용할 인증서를 생성합니다.
CSR 파일 내용을 base64로 인코딩하여 CSR_CONTENT 환경변수에 저장합니다.
```
export CSR_CONTENT=$(cat dev-user.csr | base64 | tr -d '\n')
```

[단계 5] csr.yaml 생성
CertificateSigningRequest 오브젝트에서 사용할 인증서를 환경변수 CSR_CONTENT를 사용하여 생성합니다.
```
cat <<EOF > csr.yaml
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: dev-user-csr
spec:
  request: ${CSR_CONTENT}
  signerName: kubernetes.io/kube-apiserver-client
  usages:
  - client auth
EOF

#생성된 csr.yaml 확인합니다
cat csr.yaml
```

[단계 6] 쿠버네티스에 CSR 오브젝트를 생성합니다 
```
kubectl apply -f csr.yaml
```


[단계 7] CSR 승인 
관리자 권한으로 제출된 CSR(dev-user)을 승인합니다.
```
kubectl certificate approve dev-user-csr
```

[단계 8] 서명된 인증서 추출 
승인된 CSR에서 서명된 인증서를 추출하여 dev-user.crt 파일로 저장합니다.
```
# 인증서가 발급될 때까지 잠시 기다릴 수 있습니다.
sleep 2
kubectl get csr dev-user-csr -o jsonpath='{.status.certificate}' | base64 --decode > dev-user.crt

#서명된 인증서을 확인합니다 
cat dev-user.crt

```

[단계 9] 새로운 사용자를 위한 kubectl 설정
추출된 인증서와 개인 키를 사용하여 로컬 kubeconfig 파일에 dev-user 사용자를 추가합니다.
```
kubectl config set-credentials dev-user --client-key=dev-user.key --client-certificate=dev-user.crt --embed-certs=true

#새로운 사용자가 추가된 것을 확인합니다 
cat ~/.kube/config | grep dev-user

#상세 정보를 확인합니다 
cat ~/.kube/config 
```

dev-user 사용자를 위한 컨텍스트(dev-user-context)를 생성합니다.
이 컨텍스트는 dev-user 사용자와 development 네임스페이스를 기본값으로 사용합니다.
```
kubectl config set-context dev-user-context --cluster=kubernetes --user=dev-user --namespace=development

#모든 컨텍스트 목록 확인: 
kubectl config get-contexts
```

[단계 10] 새로운 사용자로 권한 테스트
생성된 dev-user-context 컨텍스트로 전환합니다.
```
kubectl config use-context dev-user-context

#현재 어떤 컨텍스트를 사용하고 있는지 확인하려면 다음 명령어를 사용합니다.

kubectl config current-context
```

실행 명령어: kubectl get pods
```
# RBAC 정책에 의해 이 명령어는 성공해야 합니다.

```


테스트 2: 거부된 작업

```
kubectl get deployments -n development
```

서비스 조회 (실패)
pod-reader 역할에는 서비스를 조회할 권한이 없으므로 실패합니다.
```
kubectl get services -n development
```

리소스 생성 (실패)
nginx를 생성하는 파드, 디플로이먼드, 서비스를 생성하는 yaml을 실행하여 실패를 확인 합니다 
```
kubectl apply -f ../admin/deployment-nginx.yaml
```

kube-system 네임스페이스에서 파드 목록 조회
```

```

[단계 11] 정리 작업 
테스트가 완료되었으므로 원래 컨텍스트로 복구하고 생성된 설정을 삭제합니다.
```
#1. 원래 컨텍스트(kubernetes-admin@kubernetes)로 전환
```
