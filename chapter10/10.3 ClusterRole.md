ClusterRole이란?

  ClusterRole은 쿠버네티스 RBAC(역할 기반 접근 제어)에서 사용하는 권한의 집합입니다. Role과 매우 유사하지만, 결정적인 차이점은 적용 범위(Scope)에 있습니다.

   - `Role`: 특정 단일 네임스페이스 내의 리소스에 대한 권한만 정의할 수 있습니다.
   - `ClusterRole`: 클러스터 전체에 적용되는 권한을 정의합니다.

  ClusterRole은 이름 그대로 클러스터 수준의 권한을 다루기 때문에 매우 강력하며, 신중하게 사용해야 합니다.

  ClusterRole을 사용하는 경우

  ClusterRole은 주로 다음 두 가지 시나리오에서 사용됩니다.

   1. 클러스터 범위 리소스(Cluster-scoped resources)에 대한 권한을 부여할 때
       - 네임스페이스에 속하지 않는 리소스들, 예를 들어 Nodes, PersistentVolumes(PV), Namespaces, CertificateSigningRequests(CSR) 등은 Role로는 권한을 부여할 수 없고, 반드시 ClusterRole을 사용해야 합니다.

   2. 모든 네임스페이스에 걸쳐 동일한 권한을 부여할 때
       - 예를 들어, 클러스터 관리자가 모든 네임스페이스에 있는 Pod를 조회하거나 삭제하고 싶을 때 사용합니다.
       - 만약 Role을 사용한다면 모든 네임스페이스마다 똑같은 Role과 RoleBinding을 수십, 수백 개 만들어야 하므로 관리가 불가능합니다. ClusterRole 하나면 이 문제를 해결할 수 있습니다.

  ClusterRole과 ClusterRoleBinding

  ClusterRole 자체는 권한의 정의일 뿐이며, 이를 사용자나 그룹에 실제로 부여하려면 ClusterRoleBinding을 사용해야 합니다. ClusterRoleBinding은 "누가(Subject) 클러스터 전체에 걸쳐 어떤 ClusterRole을 갖는다"고 지정하는 역할을 합니다.

  ---

  예제: 스토리지 관리자(storage-admin) 역할 만들기

  클러스터의 스토리지를 관리하는 storage-admin이라는 역할을 ClusterRole로 만들고, 이 역할을 storage-master라는 사용자에게 부여하는 예제입니다.

  요구사항:
   - 모든 PersistentVolume(PV)에 대한 전체 제어 권한 (PV는 클러스터 범위 리소스)
   - 모든 StorageClass에 대한 읽기 전용 권한 (StorageClass는 클러스터 범위 리소스)
   - 모든 네임스페이스에 있는 PersistentVolumeClaim(PVC)에 대한 읽기 전용 권한 (PVC는 네임스페이스 리소스)

  1단계: ClusterRole YAML 파일 작성

  위 요구사항을 만족하는 ClusterRole을 정의합니다.
```
vi storage-admin-clusterrole.yaml

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  # ClusterRole에는 namespace 필드가 없습니다.
  name: storage-admin
rules:
# 규칙 1: PersistentVolume(클러스터 리소스)에 대한 모든 권한 부여
- apiGroups: [""]
  resources: ["persistentvolumes"]
  verbs: ["get", "list", "watch", "create", "delete", "update", "patch"]

# 규칙 2: StorageClass(클러스터 리소스)에 대한 읽기 권한 부여
- apiGroups: ["storage.k8s.io"]
  resources: ["storageclasses"]
  verbs: ["get", "list", "watch"]

# 규칙 3: 모든 네임스페이스의 PersistentVolumeClaim(네임스페이스 리소스)에 대한 읽기 권한 부여
- apiGroups: [""]
  resources: ["persistentvolumeclaims"]
  verbs: ["get", "list", "watch"]
```

  2단계: ClusterRoleBinding YAML 파일 작성

  위에서 만든 storage-admin 역할을 storage-master 사용자에게 연결합니다.

```
vi storage-admin-binding.yaml

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  # ClusterRoleBinding에도 namespace 필드가 없습니다.
  name: bind-storage-admin-to-user
subjects:
  # 이 권한을 부여받을 대상을 지정합니다.
- kind: User
  name: dev-user # 권한을 받을 사용자 이름
  apiGroup: rbac.authorization.k8s.io
- kind: User
  name: dev-user2 # 권한을 받을 사용자 이름
  apiGroup: rbac.authorization.k8s.io
roleRef:
  # 연결할 역할을 지정합니다.
  kind: ClusterRole # 반드시 ClusterRole을 참조해야 합니다.
  name: storage-admin # 1단계에서 만든 ClusterRole의 이름
  apiGroup: rbac.authorization.k8s.io
```

  3단계: 클러스터에 적용

  관리자가 위 두 파일을 클러스터에 적용합니다.
```
   kubectl apply -f storage-admin-clusterrole.yaml
   kubectl apply -f storage-admin-binding.yaml
```
  이제 storage-master라는 사용자는 자신의 인증서로 클러스터에 접속하면, 위에서 정의한 클러스터 전체의 스토리지 관련 리소스를 관리할 수 있는 권한을 갖게 됩니다.
