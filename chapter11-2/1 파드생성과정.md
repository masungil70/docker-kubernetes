쿠버네티스에서 파드가 생성되어 실제로 노드에서 실행되기까지의 과정은 여러 구성 요소가 협력하여 이루어집니다. 다음은 그 과정을 단계별로 자세히 설명한 것입니다.

   1. 파드 생성 요청 (User/Client)
       * 사용자가 kubectl apply -f my-pod.yaml과 같은 명령어를 사용하여 파드 정의(YAML/JSON)를 쿠버네티스 클러스터에 제출합니다.

   2. API 서버 수신 및 검증 (API Server)
       * kubectl 명령은 파드 정의를 쿠버네티스 API 서버로 전송합니다.
       * API 서버는 요청을 수신하고, 파드 정의의 유효성을 검사합니다 (예: 필수 필드 누락 여부, 스키마 준수 여부).
       * 어드미션 컨트롤러(Admission Controllers): 요청이 API 서버에 의해 수신된 후, 어드미션 컨트롤러가 추가적인 검증이나 변경 작업을 수행할 수 있습니다. 예를 들어, 보안 정책을 적용하거나 기본값을 주입할 수 있습니다.
       * 유효성 검사를 통과하면, API 서버는 파드 정의를 클러스터의 분산 데이터 저장소인 etcd에 저장합니다. 이 시점에서 파드는 생성되었지만, 아직 어떤 노드에도 할당되지 않은 "Pending" 상태입니다.

   3. 스케줄링 (Scheduler)
       * 스케줄러(kube-scheduler)는 API 서버를 지속적으로 감시하며, 아직 nodeName이 할당되지 않은 새로운 파드(즉, 스케줄링되지 않은 파드)를 찾습니다.
       * 스케줄러는 발견된 파드에 대해 적절한 노드를 찾기 위해 다음 단계를 수행합니다:
           * 필터링(Filtering): 파드의 리소스 요구사항(CPU, 메모리), 노드 셀렉터(nodeSelector), 테인트(Taints) 및 톨러레이션(Tolerations), 노드 어피니티(Node Affinity) 및 안티-어피니티(Anti-Affinity) 등 다양한 제약 조건을 기반으로 파드를 실행할 수 있는 적합한 노드 목록을 필터링합니다.
           * 스코어링(Scoring): 필터링된 노드들에 대해 점수를 매겨 가장 적합한 노드를 선택합니다 (예: 리소스 사용률이 낮은 노드, 특정 레이블이 있는 노드 등).
       * 가장 적합한 노드를 선택한 후, 스케줄러는 API 서버에 파드의 nodeName 필드를 업데이트하여 해당 파드를 선택된 노드에 "바인딩"합니다. 파드의 상태는 여전히 "Pending"이지만, 이제 특정 노드에 할당되었습니다.

   4. 노드에서의 파드 실행 (Kubelet)
       * 각 워커 노드에서 실행되는 kubelet은 API 서버를 지속적으로 감시하며, 자신의 노드에 할당된 파드(즉, nodeName이 자신의 노드 이름과 일치하는 파드)를 찾습니다.
       * kubelet이 자신에게 할당된 파드를 감지하면, 다음 작업을 수행합니다:
           * CRI (Container Runtime Interface) 호출: kubelet은 컨테이너 런타임(Container Runtime) (예: containerd, CRI-O, Docker)과 통신하기 위해 CRI를 사용합니다.
           * 이미지 풀(Image Pull): 컨테이너 런타임은 파드 정의에 명시된 컨테이너 이미지(들)가 로컬에 없으면, Docker Hub나 다른 컨테이너 레지스트리에서 이미지를 다운로드(pull)합니다.
           * CNI (Container Network Interface) 호출: kubelet은 CNI 플러그인 (예: Calico, Flannel)과 통신하여 파드에 네트워크를 구성합니다. 여기에는 파드에 IP 주소를 할당하고, 네트워크 네임스페이스를 설정하며, 필요한 네트워크 규칙을 구성하는 작업이 포함됩니다.
           * CSI (Container Storage Interface) 호출 (선택 사항): 파드가 영구 스토리지(Persistent Volume)를 필요로 하는 경우, kubelet은 CSI 드라이버와 통신하여 볼륨을 프로비저닝하고 파드에 연결합니다.
           * 컨테이너 생성 및 시작: 컨테이너 런타임은 파드의 cgroups 및 네임스페이스 내에서 컨테이너(들)를 생성하고 시작합니다. 이 시점에서 파드의 상태는 "ContainerCreating"으로 변경될 수 있습니다.

   5. 상태 보고 및 준비 (Kubelet & API Server)
       * kubelet은 파드의 현재 상태(예: "Pending", "ContainerCreating", "Running", "Ready")를 지속적으로 API 서버에 보고합니다.
       * 파드 내의 모든 컨테이너가 성공적으로 시작되고, 정의된 모든 프로브(liveness probe, readiness probe)가 성공적으로 통과되면, 파드의 상태는 "Running" 및 "Ready"로 변경됩니다.
       * 이제 파드는 트래픽을 수신할 준비가 된 것입니다.

  이러한 과정을 통해 사용자가 파드를 생성하는 요청을 보내면, 쿠버네티스 클러스터의 여러 핵심 구성 요소들이 유기적으로 작동하여 파드가 최종적으로 노드에서 실행되게 됩니다.

```
 +-------------------+     1. kubectl apply -f pod.yaml     +-------------------+
 | User / kubectl    | -----------------------------------> | API Server        |
 +-------------------+                                      +---------+---------+
                                                                      |
                                                                      | 2. 파드 정의 저장
                                                                      v
                                                              +-------+-------+
                                                              | etcd          |
                                                              +---------------+
                                                                      ^
                                                                      | 3. 스케줄링되지 않은 파드 감시

 | Scheduler         | <--------------------------------------| API Server        |
 | (kube-scheduler)  |                                        +---------+---------+
 +---------+---------+                                                  |
           |                                                            | 4. 파드에 노드 할당 (Binding)
           | 5. 최적의 노드 선택 및 바인딩                              |
           v                                                            v
 +-------------------+                                        +-------+-------+
 | API Server        | <--------------------------------------| API Server    |
 +---------+---------+                                        +---------+-----+
           |                                                            |
           | 6. 할당된 파드 감시                                        | 7. 파드 정보 전달
           v                                                            v
 +-------------------+                                        +-------+-------+
 | Kubelet (on Node) | -------------------------------------> | Container     |
 +---------+---------+                                        | Runtime (CRI) |
           |                                                  +-------+-------+
           | 8. 이미지 풀, 네트워크/스토리지 설정, 컨테이너 실행
           v
 +-------------------+

 |  +-------------+  |
 |  | Pod         |  |

 |  |  +-------+  |  |
 |  |  +-------+  |  |
 |  |  | Ctnr2 |  |  |
 |  |  +-------+  |  |
 |  +-------------+  |
 +-------------------+
           ^
           | 9. 파드 상태 보고
           |
 +-------------------+
 | API Server        |
 +-------------------+
```
  설명:

   1. User / kubectl: 사용자가 kubectl apply 명령으로 파드 정의를 쿠버네티스 클러스터에 제출합니다.
   2. API Server: API 서버는 이 요청을 받아 파드 정의의 유효성을 검사하고, 클러스터의 상태를 저장하는 etcd에 파드 정보를 기록합니다. 이 시점에서 파드는 "Pending" 상태입니다.
   3. Scheduler: 스케줄러는 API 서버를 감시하며, 아직 노드에 할당되지 않은 파드를 찾습니다.
   4. Scheduler -> API Server: 스케줄러는 파드의 리소스 요구사항, 노드 제약 조건 등을 고려하여 파드를 실행할 최적의 노드를 선택하고, 해당 파드를 선택된 노드에 "바인딩"합니다. 이 정보는 다시 API 서버를 통해 etcd에 기록됩니다.
   5. Kubelet (on Node): 각 노드에서 실행되는 Kubelet은 API 서버를 감시하며, 자신에게 할당된 파드(즉, nodeName이 자신의 노드 이름과 일치하는 파드)를 감지합니다.
   6. Kubelet -> Container Runtime: Kubelet은 파드 정보를 컨테이너 런타임(예: containerd, CRI-O)에 전달합니다. 컨테이너 런타임은 필요한 컨테이너 이미지를 풀(pull)하고, CNI(네트워크) 및 CSI(스토리지) 플러그인과 협력하여 파드의 네트워크 및 스토리지를 설정합니다.
   7. Node: 컨테이너 런타임은 최종적으로 노드 상에 파드 내의 컨테이너들을 생성하고 실행합니다.
   8. Kubelet -> API Server: Kubelet은 파드의 실행 상태(예: Running, Ready)를 지속적으로 API 서버에 보고합니다.

  이 과정을 통해 파드는 사용자의 요청으로부터 시작하여 최종적으로 노드에서 실행되는 생명주기를 거치게 됩니다.
