
✦ 쿠버네티스 노드에서 레이블을 관리하는 것은 파드 스케줄링을 제어하고 클러스터 리소스를 효율적으로 활용하는 데 매우 중요합니다. 다음은 노드 레이블을 관리하는 자세한 방법과 관련 개념입니다.

  ---

  1. 노드 레이블이란?

  노드 레이블은 쿠버네티스 노드에 할당하는 키-값(key-value) 쌍의 메타데이터입니다. 이 레이블은 노드의 특성(예: 하드웨어 유형, 위치, 역할 등)을 식별하는 데 사용됩니다. 파드를 배포할 때 nodeSelector나 nodeAffinity와 같은 스케줄링 규칙을 사용하여 특정 레이블을 가진 노드에만 파드가 배포되도록 지정할 수 있습니다.

  ---

  2. 노드 레이블을 사용하는 이유 (활용 사례)

   * 하드웨어 특성 기반 스케줄링: GPU, SSD, 특정 CPU 아키텍처 등 특정 하드웨어 리소스가 있는 노드에만 특정 워크로드를 배포합니다.
       * 예: gpu=true, disktype=ssd, arch=arm64
   * 지리적 위치/가용성 존 분리: 파드를 특정 데이터센터, 리전, 가용성 존에 있는 노드에 배포하여 고가용성 또는 지역적 규제를 준수합니다.
       * 예: region=us-east-1, zone=us-east-1a
   * 노드 역할 정의: 마스터 노드, 워커 노드, 엣지 노드 등 노드의 역할을 명확히 구분합니다.
       * 예: node-role.kubernetes.io/control-plane="", node-role.kubernetes.io/worker=""
   * 환경 분리: 개발, 테스트, 프로덕션 환경을 물리적으로 분리된 노드 그룹에 배포합니다.
       * 예: env=prod, env=dev
   * 라이선스 관리: 특정 라이선스가 필요한 소프트웨어를 해당 라이선스가 적용된 노드에만 배포합니다.
       * 예: license=special-db

  ---

  3. 노드 레이블 관리 방법

  kubectl label nodes 명령어를 사용하여 노드 레이블을 관리합니다.

  3.1. 노드 레이블 확인하기

  모든 노드의 레이블 확인:
```
kubectl get nodes --show-labels
```
  특정 노드의 자세한 정보와 레이블 확인:
```
   kubectl describe node <노드-이름>
```
  예시:
```  
   kubectl describe node worker-node-1
```
  출력의 Labels: 섹션에서 해당 노드의 모든 레이블을 확인할 수 있습니다.

  3.2. 노드에 레이블 추가/업데이트하기

  새로운 레이블 추가:
```
   kubectl label nodes <노드-이름> <키>=<값>
```
  예시: worker-node-1에 disktype=ssd 레이블 추가
```
   kubectl label nodes worker-node-1 disktype=ssd
```
  기존 레이블 값 업데이트 (덮어쓰기):

  이미 존재하는 레이블의 값을 변경하려면 --overwrite 플래그를 사용해야 합니다.
```
   kubectl label nodes <노드-이름> <키>=<새로운-값> --overwrite
```
  예시: worker-node-1의 disktype 레이블을 nvme로 변경
```
   kubectl label nodes worker-node-1 disktype=nvme --overwrite
```
  3.3. 노드에서 레이블 제거하기

  레이블을 제거하려면 레이블 키 뒤에 하이픈(-)을 붙입니다.
```
   kubectl label nodes <노드-이름> <키>-
```
  예시: worker-node-1에서 disktype 레이블 제거
```
   kubectl label nodes worker-node-1 disktype-
```
  ---

  4. 노드 레이블 사용 시 모범 사례

   * 의미 있는 이름 사용: 레이블 키와 값은 노드의 특성을 명확하게 나타내도록 의미 있게 작성합니다. (예: hardware-type, location, role)
   * 일관성 유지: 클러스터 전체에서 레이블 명명 규칙과 값의 일관성을 유지합니다.
   * 과도한 레이블링 피하기: 필요한 경우에만 레이블을 사용하고, 너무 많은 레이블을 추가하여 복잡성을 높이지 않도록 합니다.
   * 쿠버네티스 예약 레이블 이해: kubernetes.io/hostname, beta.kubernetes.io/os, node-role.kubernetes.io/<role> 등 쿠버네티스에서 내부적으로 사용하거나 권장하는 레이블이 있습니다. 이들을 이해하고 필요에 따라 활용합니다.
   * 스케줄링 규칙과 함께 사용:
       * `nodeSelector`: 가장 간단한 방법으로, 정확히 일치하는 레이블을 가진 노드에 파드를 스케줄링합니다.
       * `nodeAffinity`: nodeSelector보다 유연하고 강력한 스케줄링 규칙을 제공합니다. requiredDuringSchedulingIgnoredDuringExecution (필수) 또는 preferredDuringSchedulingIgnoredDuringExecution (선호)과 같은 옵션을 사용하여 더 복잡한 조건을 정의할 수 있습니다.
       * `Taints`와 `Tolerations`: 특정 노드에 파드가 스케줄링되는 것을 "방지"하거나, 특정 파드만 해당 노드에 스케줄링되도록 허용하는 데 사용됩니다. 레이블과는 반대 개념으로 작동합니다.

  노드 레이블을 효과적으로 관리하면 쿠버네티스 클러스터의 리소스 활용도를 높이고, 워크로드의 안정성과 성능을 최적화할 수 있습니다.

---
  
  1. NodeSelector (노드 셀렉터)

  목적: 파드를 특정 노드에 배치하는 가장 간단하고 직접적인 방법입니다. 노드에 부여된 레이블(label)을 기반으로 파드를 스케줄링합니다.

  작동 방식:
  파드 정의의 spec.nodeSelector 필드에 key: value 형태의 레이블을 지정합니다. 스케줄러는 이 레이블과 정확히 일치하는 레이블을 가진 노드에만 파드를 스케줄링합니다.

  특징:
   * 단순성: 사용하기 매우 간단합니다.
   * 정확한 일치: 지정된 레이블과 정확히 일치하는 노드만 선택합니다. OR 조건이나 NOT 조건과 같은 복잡한 논리는 지원하지 않습니다.
   * 강제성: 지정된 레이블을 가진 노드가 없으면 파드는 스케줄링되지 않고 "Pending" 상태로 남습니다.

  예시:
  disktype: ssd 레이블이 있는 노드에만 파드를 스케줄링합니다.
```
apiVersion: v1
kind: Pod
metadata:
  name: my-pod-with-nodeselector
spec:
  nodeSelector:
    disktype: ssd  # 이 레이블을 가진 노드에만 스케줄링
  containers:
  - name: nginx
    image: nginx
```

  2. Node Affinity (노드 어피니티)

  목적: NodeSelector보다 더 유연하고 표현력이 풍부한 방법으로 파드를 특정 노드에 배치합니다. 복잡한 매칭 규칙(예: In, NotIn, Exists)과 "선호(preferred)" 규칙을 지원합니다.

  작동 방식:
  파드 정의의 spec.affinity.nodeAffinity 필드에 규칙을 정의합니다.

  두 가지 주요 타입:

   1. `requiredDuringSchedulingIgnoredDuringExecution` (필수 어피니티)
       * 설명: 파드가 스케줄링될 때 반드시 충족되어야 하는 하드(hard) 규칙입니다. 이 규칙을 만족하는 노드가 없으면 파드는 스케줄링되지 않습니다.
       * `IgnoredDuringExecution`의 의미: 파드가 일단 노드에 스케줄링된 후에는, 해당 노드의 레이블이 변경되어 더 이상 이 규칙을 만족하지 않더라도 파드는 해당 노드에서 계속 실행됩니다. 즉, 이미 실행 중인 파드를 노드에서 제거(evict)하지 않습니다.

      예시: disktype 레이블이 ssd 또는 hdd인 노드에만 스케줄링합니다.
```
apiVersion: v1
kind: Pod
metadata:
  name: my-pod-required-node-affinity
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disktype
            operator: In  # 'In' 연산자 사용
            values:
            - ssd
            - hdd
  containers:
  - name: nginx
    image: nginx
```
   2. `preferredDuringSchedulingIgnoredDuringExecution` (선호 어피니티)
       * 설명: 파드가 스케줄링될 때 가능한 한 충족되기를 선호하는 소프트(soft) 규칙입니다. 이 규칙을 만족하는 노드가 있으면 해당 노드에 스케줄링되지만, 없더라도 다른 노드에 스케줄링될 수 있습니다.
       * `IgnoredDuringExecution`의 의미: requiredDuringSchedulingIgnoredDuringExecution와 동일하게, 일단 스케줄링된 후에는 노드 레이블이 변경되어도 파드를 제거하지 않습니다.

      예시: disktype: ssd 레이블이 있는 노드를 선호하지만, 없으면 다른 노드에도 스케줄링될 수 있습니다.
```
apiVersion: v1
kind: Pod
metadata:
  name: my-pod-preferred-node-affinity
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100  # 가중치 (1-100). 높을수록 선호도가 높음.
        preference:
          matchExpressions:
          - key: disktype
            operator: In
            values:
            - ssd
  containers:
  - name: nginx
    image: nginx
```
  Node Affinity의 연산자 (`operator`):
   * In: 레이블 값이 values 목록 중 하나와 일치해야 합니다.
   * NotIn: 레이블 값이 values 목록 중 어느 것과도 일치하지 않아야 합니다.
   * Exists: 해당 키를 가진 레이블이 존재해야 합니다 (값은 상관 없음).
   * DoesNotExist: 해당 키를 가진 레이블이 존재하지 않아야 합니다.
   * Gt: 레이블 값이 지정된 값보다 커야 합니다 (숫자 값에만 해당).
   * Lt: 레이블 값이 지정된 값보다 작아야 합니다 (숫자 값에만 해당).

  3. Pod Affinity and Anti-affinity (파드 어피니티 및 안티-어피니티)

  목적: 파드를 다른 파드의 레이블을 기반으로 스케줄링하는 메커니즘입니다. 즉, 특정 파드들이 함께(affinity) 또는 떨어져서(anti-affinity) 스케줄링되도록 합니다.

  작동 방식:
  파드 정의의 spec.affinity.podAffinity 또는 spec.affinity.podAntiAffinity 필드에 규칙을 정의합니다.

  핵심 개념: `topologyKey`
  topologyKey는 어피니티/안티-어피니티 규칙이 적용될 "토폴로지"의 범위를 정의합니다. 즉, 어떤 범위 내에서 다른 파드를 찾을 것인지를 지정합니다.
   * kubernetes.io/hostname: 동일한 노드 내에서.
   * topology.kubernetes.io/zone: 동일한 가용성 존(Zone) 내에서.
   * topology.kubernetes.io/region: 동일한 리전(Region) 내에서.
   * 사용자 정의 레이블: 클러스터 관리자가 정의한 다른 레이블 (예: rack).

  두 가지 주요 타입 (Node Affinity와 유사):
   1. `requiredDuringSchedulingIgnoredDuringExecution` (필수 어피니티/안티-어피니티)
       * 설명: 스케줄링 시 반드시 충족되어야 하는 하드 규칙입니다.
   2. `preferredDuringSchedulingIgnoredDuringExecution` (선호 어피니티/안티-어피니티)
       * 설명: 스케줄링 시 가능한 한 충족되기를 선호하는 소프트 규칙입니다.

  ---

  3.1. Pod Affinity (파드 어피니티)

  목적: 특정 레이블을 가진 다른 파드와 함께 스케줄링되도록 합니다. 주로 성능 향상(예: 프론트엔드와 백엔드 파드를 동일 노드에 배치하여 네트워크 지연 감소)을 위해 사용됩니다.

  예시: app: backend 레이블을 가진 파드가 있는 동일한 노드에 스케줄링합니다.
```
apiVersion: v1
kind: Pod
metadata:
  name: my-frontend-pod
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: backend  # 'app: backend' 레이블을 가진 파드를 찾음
        topologyKey: kubernetes.io/hostname # 동일한 노드 내에서 찾음
  containers:
  - name: frontend
    image: frontend-image
```
  ---

  3.2. Pod Anti-affinity (파드 안티-어피니티)

  목적: 특정 레이블을 가진 다른 파드와 떨어져서 스케줄링되도록 합니다. 주로 고가용성(High Availability)을 위해 사용됩니다. 예를 들어, 동일한 애플리케이션의 여러 복제본이 단일 장애 지점(예: 노드)에 집중되지 않도록 분산 배치합니다.

  예시: app: my-app 레이블을 가진 다른 파드가 있는 동일한 노드에는 스케줄링하지 않습니다.
```
apiVersion: v1
kind: Pod
metadata:
  name: my-app-replica-1
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: my-app  # 'app: my-app' 레이블을 가진 파드를 찾음
        topologyKey: kubernetes.io/hostname # 동일한 노드 내에서 찾음
  containers:
  - name: my-app
    image: my-app-image
```
