
✦ Kubernetes(k8s) 파드(Pod)의 생명 주기(Lifecycle)는 파드가 생성되어 소멸하기까지의 과정을 의미하며, 여러 단계와 상태(Phase)로 구성됩니다.

  파드의 생명 주기는 크게 3가지 핵심 개념으로 이해할 수 있습니다.

   1. 파드의 단계 (Pod Phase): 파드의 현재 상태를 나타내는 고수준의 요약.
   2. 컨테이너의 상태 (Container State): 파드 내부 각 컨테이너의 상세한 상태.
   3. 생명 주기 제어 메커니즘: 파드의 시작, 동작, 종료를 제어하는 훅(Hook)과 프로브(Probe).

  ---

  1. 파드의 단계 (Pod Phase)

  파드는 항상 다음 5가지 단계 중 하나에 속합니다. kubectl get pods를 실행했을 때 STATUS 열에 표시되는 값입니다.


  | 단계 (Phase)| 설명|
  |--- | --- |
  | `Pending` (보류)|파드가 쿠버네티스 클러스터에 의해 승인되었지만, 아직 하나 이상의 컨테이너가 생성되지 않은 상태입니다.주요 원인: 스케줄러가 파드를 할당할 적절한 노드를 찾고 있는 중 / 노드는 결정되었으나 컨테이너 이미지를 다운로드하는 중.|
  | `Running` (실행 중)|파드가 노드에 성공적으로 할당되었고, 모든 컨테이너가 생성된 상태입니다.중요: 이 상태가 반드시 "파드가 정상적으로 서비스 가능함"을 의미하지는 않습니다. 최소 하나 이상의 컨테이너가 실행 중이거나, 시작 또는 종료 과정에 있음을 나타냅니다. (자세한 상태는 프로브로 확인)|
  |`Succeeded` (성공)|파드 내의 모든 컨테이너가 성공적으로 (Exit Code 0) 종료된 상태입니다.이 파드는 재시작되지 않습니다. 주로 Job이나 일회성 작업을 실행할 때 나타납니다.| 
  |`Failed` (실패)| 파드 내의 컨테이너 중 하나 이상이 실패(Exit Code가 0이 아님)로 종료된 상태입니다.restartPolicy에 따라 컨테이너가 재시작될 수도 있지만, 특정 조건 하에 파드 자체가 이 단계로 전환됩니다.|
  |` `Unknown` (알 수 없음)|<li>보통 노드와의 통신 문제로 파드의 상태를 확인할 수 없는 경우입니다.Kubelet(노드 에이전트)이 마스터와 통신이 두절되면 이런 상태가 될 수 있습니다.|

  ---

  2. 컨테이너의 상태 (Container State)

  파드의 단계는 내부 컨테이너들의 상태에 따라 결정됩니다. kubectl describe pod <pod-name>으로 상세히 볼 수 있습니다.


  |상태 (State)|설명|
  |--- | --- |
  | `Waiting` (대기)|컨테이너가 실행에 필요한 사전 작업을 수행 중인 상태입니다.주요 원인: 컨테이너 이미지를 레지스트리에서 다운로드(ImagePulling), 시크릿(Secret)이나 컨피그맵(ConfigMap) 데이터를 기다리는 중, initContainer가 실행 중일 때.|
  |`Running` (실행 중)|컨테이너가 문제없이 실행되고 있는 상태입니다.이때 postStart 훅이 실행될 수 있습니다.|
  |`Terminated` (종료)| 컨테이너가 실행을 시작했다가 종료된 상태입니다.성공적으로 완료되었거나, 실패했거나, 메모리 부족(OOM) 등으로 시스템에 의해 강제 종료된 경우 모두 해당합니다. 종료 이유와 Exit Code를 확인할 수 있습니다. 이때 preStop 훅이 실행될 수 있습니다.|

  3. 생명 주기 제어 메커니즘

  쿠버네티스는 파드의 생명 주기에 개입하여 더 정교하게 제어할 수 있는 장치들을 제공합니다.

  가. 초기화 컨테이너 (Init Containers)

   * 역할: 앱 컨테이너가 시작되기 전에 실행되어야 하는 사전 작업을 담당합니다.
   * 특징:
       * 여러 개가 있다면 순차적으로 실행됩니다. (첫 번째 Init 컨테이너 성공 → 두 번째 Init 컨테이너 실행)
       * 모든 Init 컨테이너가 성공적으로(Exit Code 0) 완료되어야만 앱 컨테이너가 시작됩니다.
       * 사용 예: 필요한 설정 파일 생성, 외부 서비스가 준비될 때까지 대기, 데이터베이스 스키마 마이그레이션 등.

  나. 생명 주기 훅 (Lifecycle Hooks)

  컨테이너의 생명 주기에서 특정 이벤트 발생 시 실행되는 코드입니다.

   * `postStart`: 컨테이너가 생성된 직후에 실행됩니다. 컨테이너의 메인 프로세스(Entrypoint)와 비동기적으로 실행되며, 이 훅이 완료될 때까지 기다리지 않습니다.
       * 사용 예: 컨테이너가 특정 초기화 작업을 수행하도록 할 때 (단, Init 컨테이너와 달리 메인 프로세스와 병렬 실행)
   * `preStop`: 컨테이너가 종료되기 직전에 호출됩니다. 컨테이너에 SIGTERM 신호가 전송되기 전에 실행되며, 이 훅이 완료될 때까지 동기적으로 대기합니다.
       * 사용 예: 진행 중이던 요청을 모두 처리하고 연결을 정상적으로 끊는 Graceful Shutdown 구현.

  다. 프로브 (Probes): 컨테이너 상태 검사

  Kubelet이 컨테이너의 상태를 주기적으로 확인하는 방법입니다.

   * `livenessProbe` (생존 프로브): "컨테이너가 살아있는가?"
       * 프로브가 실패하면, Kubelet은 컨테이너가 응답 없는 상태(Deadlock 등)로 간주하고 컨테이너를 재시작시킵니다.
   * `readinessProbe` (준비 프로브): "컨테이너가 요청을 처리할 준비가 되었는가?"
       * 프로브가 실패하면, 컨테이너는 재시작되지 않지만 서비스(Service)의 엔드포인트 목록에서 제외됩니다. 즉, 트래픽을 받지 않게 됩니다. 앱이 시작은 되었지만, 내부적으로 캐시를 데우거나 하는 등의 준비 시간이 필요할 때 유용합니다.
   * `startupProbe` (시작 프로브): "컨테이너가 시작되었는가?"
       * 시작하는 데 오래 걸리는 애플리케이션을 위한 프로브입니다.
       * 이 프로브가 성공할 때까지 livenessProbe와 readinessProbe는 비활성화됩니다. 프로브가 성공하면 그 이후부터는 다른 프로브들이 동작합니다.
       * 프로브가 설정된 failureThreshold 횟수만큼 실패하면 컨테이너는 재시작됩니다.


  파드 생명 주기 전체 흐름 요약

   1. 생성 (Creation)
       * 사용자가 kubectl apply 등으로 파드 생성 요청.
       * API 서버가 요청을 받아 etcd에 파드 객체 저장.
       * 스케줄러가 파드를 실행할 최적의 노드를 찾아 할당. (→ Pending 상태)

   2. 시작 (Startup)
       * 노드의 Kubelet이 자신에게 할당된 파드를 감지.
       * 컨테이너 런타임(예: containerd)을 통해 컨테이너 이미지 다운로드. (→ Pending 상태, Container Waiting)
       * Init Container(들) 순차적 실행.
       * App Container(들) 병렬 실행.
       * 컨테이너 생성 직후 `postStart` 훅 실행.
       * 모든 컨테이너가 실행되면 파드는 Running 상태로 전환.

   3. 실행 중 (Running)
       * Kubelet이 주기적으로 `livenessProbe`와 `readinessProbe` 실행.
       * livenessProbe 실패 → 컨테이너 재시작.
       * readinessProbe 실패 → 서비스에서 제외 → 성공 시 다시 포함.

   4. 종료 (Termination)
       * 사용자가 kubectl delete 등으로 파드 삭제 요청.
       * 파드가 Terminating 상태로 변경되고, readinessProbe가 비활성화되어 서비스에서 제외됨.
       * `preStop` 훅 실행.
       * 훅 실행이 끝나면 컨테이너의 메인 프로세스에 `SIGTERM` 신호 전송.
       * 애플리케이션이 SIGTERM을 받고 정상 종료(Graceful Shutdown)할 시간을 줌 (terminationGracePeriodSeconds, 기본 30초).
       * Grace Period가 지나도 컨테이너가 종료되지 않으면 `SIGKILL` 신호를 보내 강제 종료.
       * 노드에서 파드의 모든 리소스가 정리되면 API 서버에서 파드 객체 최종 삭제.
