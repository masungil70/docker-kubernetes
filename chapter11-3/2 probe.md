 ### 프로브(Probe)란 

 "프로브(Probe)"는 컨테이너의 상태를 주기적으로 진단하여 컨테이너가 정상적으로 작동하고 있는지,   트래픽을 처리할 준비가 되었는지 등을 확인하는 메커니즘입니다. 프로브는 컨테이너의 생명주기를 관리하고 애플리케이션의  안정성과 가용성을 높이는 데 필수적인 요소입니다.

  프로브의 일반적인 목적 및 중요성:

   * 컨테이너 상태 확인: 컨테이너 내부의 애플리케이션이 실제로 실행 중이고 응답하는지 확인합니다. 단순히 프로세스가 살아있는 것만으로는 애플리케이션이 정상이라고 볼 수 없는 경우가 많습니다(예: 데드락, 메모리 누수 등으로 인해 응답하지 않는 상태).
   * 서비스 가용성 보장: 준비되지 않은 컨테이너로 트래픽이 전송되는 것을 방지하여 사용자 경험을 개선하고 서비스의 안정성을 유지합니다.
   * 자동 복구: 비정상적인 컨테이너를 자동으로 감지하고 재시작하거나 서비스에서 격리하여 수동 개입 없이도 애플리케이션의 복원력을 높입니다.

  주요 프로브 유형:

  쿠버네티스는 세 가지 주요 프로브 유형을 제공하며, 각각 다른 목적을 가집니다.

   1. Liveness Probe (활성 프로브):
       * 목적: 컨테이너가 살아있고 정상적으로 작동하는지 확인합니다. 애플리케이션이 데드락에 빠지거나 응답하지 않는 상태를 감지하는 데 사용됩니다.
       * 실패 시 조치: 프로브가 실패하면 쿠버네티스는 해당 컨테이너를 종료하고 재시작합니다.
       * 예시: 웹 서버가 응답하지 않거나, 데이터베이스 연결이 끊어져 쿼리를 처리할 수 없는 경우.

   2. Readiness Probe (준비 프로브):
       * 목적: 컨테이너가 들어오는 트래픽을 처리할 준비가 되었는지 확인합니다. 애플리케이션이 시작하는 데 시간이 걸리거나, 외부 종속성(데이터베이스, 캐시 등)에 연결해야 하는 경우에 유용합니다.
       * 실패 시 조치: 프로브가 실패하면 쿠버네티스는 해당 컨테이너로 트래픽을 보내는 것을 중단합니다(서비스의 엔드포인트 목록에서 제거). 컨테이너는 계속 실행되며, 프로브가 다시 성공하면 트래픽을 다시 받기 시작합니다. 컨테이너를 재시작하지 않습니다.
       * 예시: 애플리케이션이 시작 중이거나, 데이터베이스 연결이 일시적으로 끊어져 쿼리를 처리할 수 없는 경우.

   3. Startup Probe (시작 프로브):
       * 목적: 컨테이너 내의 애플리케이션이 성공적으로 시작되었는지 확인합니다. 특히 시작 시간이 긴 레거시 애플리케이션에 유용합니다.
       * 작동 방식: 이 프로브가 성공할 때까지 다른 프로브(liveness, readiness)는 비활성화됩니다. startup probe가 성공하면 다른 프로브가 활성화되어 정상적인 컨테이너 상태 관리를 시작합니다.
       * 실패 시 조치: 프로브가 실패하면 컨테이너를 종료하고 재시작합니다.
       * 예시: 애플리케이션이 매우 느리게 시작되어 initialDelaySeconds만으로는 충분하지 않은 경우.

  공통 프로브 핸들러 (Probe Handlers):

  각 프로브 유형은 컨테이너의 상태를 확인하기 위해 다음 세 가지 방법 중 하나를 사용합니다.

   1. `ExecAction` (명령 실행): 컨테이너 내부에서 지정된 명령을 실행하고, 명령의 종료 코드(0은 성공, 0이 아니면 실패)를 확인합니다.
   2. `HTTPGetAction` (HTTP 요청): 지정된 경로로 HTTP GET 요청을 보내고, 응답 코드(2xx 또는 3xx는 성공)를 확인합니다.
   3. `TCPSocketAction` (TCP 소켓): 지정된 포트로 TCP 연결을 시도하고, 연결 성공 여부를 확인합니다.

  공통 매개변수:

  모든 프로브 유형은 다음과 같은 공통 매개변수를 가집니다.

   * `initialDelaySeconds`: 컨테이너 시작 후 프로브가 시작되기까지의 초기 지연 시간.
   * `periodSeconds`: 프로브를 실행하는 주기.
   * `timeoutSeconds`: 프로브가 타임아웃되는 시간.
   * `successThreshold`: 프로브가 성공으로 간주되기 위한 연속 성공 횟수.
   * `failureThreshold`: 프로브가 실패로 간주되기 위한 연속 실패 횟수.

  결론:
  프로브는 쿠버네티스 환경에서 애플리케이션의 건강 상태를 지속적으로 모니터링하고, 문제가 발생했을 때 자동으로 복구 메커니즘을 트리거하여 서비스의 안정성과 신뢰성을 크게 향상시키는 핵심 기능입니다.

### Liveness Probe (활성 프로브)
livenessProbe는 쿠버네티스에서 파드 내 컨테이너의 상태를 진단하는 프로브입니다. 주된 목적은 컨테이너가 여전히 실행 중이고 정상적인지 확인하는 것입니다. 만약 liveness probe가 실패하면, 쿠버네티스는 해당 컨테이너를 비정상으로 간주하고 재시작합니다.

  자세한 설명은 다음과 같습니다:

  목적:
  liveness probe의 주요 목표는 애플리케이션이 실행 중이지만 진행할 수 없는 상황(예: 데드락, 메모리 고갈, 응답 없음 등)을 감지하는 것입니다. liveness probe가 없으면 쿠버네티스는 프로세스가 실행 중인 한 컨테이너가 정상이라고 가정합니다. 만약 애플리케이션이 고장 난 상태가 되었지만 프로세스가 충돌하지 않는다면, 쿠버네티스는 이를 재시작해야 할지 알 수 없게 되어 겉으로는 "실행 중"이지만 실제로는 작동하지 않는 서비스가 됩니다.

  작동 방식:
  쿠버네티스는 구성된 liveness probe를 컨테이너에 주기적으로 실행합니다. 프로브가 성공적인 상태(예: HTTP 200, 명령 종료 코드 0)를 반환하면 컨테이너는 정상으로 간주됩니다. 실패 상태(예: HTTP 500, 0이 아닌 명령 종료 코드)를 반환하면 컨테이너는 비정상으로 간주됩니다.

  실패 시 조치:
  liveness probe가 실패하면 쿠버네티스는 다음 조치를 취합니다:
   1. 컨테이너를 비정상으로 표시합니다.
   2. 비정상 컨테이너를 종료합니다.
   3. 컨테이너를 재시작합니다(파드의 restartPolicy에 따라, 일반적으로 배포 및 StatefulSet의 경우 Always).

  liveness probe의 종류:
  쿠버네티스는 세 가지 주요 유형의 liveness probe를 지원합니다:

   1. `ExecAction` (명령 프로브):
       * 컨테이너 내부에서 지정된 명령을 실행합니다.
       * 명령이 상태 코드 0으로 종료되면 프로브는 성공으로 간주됩니다.
       * 예시: command: ["cat", "/tmp/healthy"] (파일 존재 여부 확인) 또는 command: ["/bin/check-app-health.sh"] (사용자 정의 스크립트 실행). MariaDB 예시에서 사용한 방식입니다.

   2. `HTTPGetAction` (HTTP 프로브):
       * 지정된 IP 주소, 포트 및 경로에 HTTP GET 요청을 수행합니다.
       * HTTP 응답 코드가 2xx 또는 3xx이면 프로브는 성공으로 간주됩니다.
       * 예시: httpGet: { path: /healthz, port: 8080 }

   3. `TCPSocketAction` (TCP 프로브):
       * 지정된 포트에서 TCP 소켓을 열려고 시도합니다.
       * TCP 연결이 설정되면 프로브는 성공으로 간주됩니다.
       * 예시: tcpSocket: { port: 8080 } (포트가 열려 있고 수신 대기 중인지 확인).

  주요 매개변수:

   * `initialDelaySeconds`: (선택 사항) 컨테이너가 시작된 후 liveness probe가 시작되기까지 기다리는 시간(초)입니다. 애플리케이션이 시작되고 준비될 시간을 줍니다.
   * `periodSeconds`: (선택 사항) 프로브를 수행하는 빈도(초)입니다. 기본값은 10초입니다.
   * `timeoutSeconds`: (선택 사항) 프로브가 타임아웃되는 시간(초)입니다. 기본값은 1초입니다. 프로브가 이 시간보다 오래 걸리면 실패로 간주됩니다.
   * `successThreshold`: (선택 사항) 프로브가 실패한 후 성공으로 간주되기 위한 최소 연속 성공 횟수입니다. 기본값은 1입니다.
   * `failureThreshold`: (선택 사항) 프로브가 실패로 간주되어 컨테이너가 재시작되기 위한 최소 연속 실패 횟수입니다. 기본값은 3입니다.

  모범 사례 및 고려 사항:

   * 가볍고 빠르게: 프로브는 매우 가볍고 빠르게 실행되어야 합니다. 자주 실행되므로 느린 프로브는 리소스를 소비하거나 불필요한 재시작을 유발할 수 있습니다.
   * Readiness와 중복되지 않게: liveness probe는 애플리케이션이 살아있는지 확인해야 하며, 반드시 트래픽을 처리할 준비가 되었는지 확인할 필요는 없습니다. Readiness probe는 "트래픽을 처리할 준비가 되었는지" 측면을 처리합니다.
   * 외부 종속성 피하기(가능하다면): liveness probe는 이상적으로 애플리케이션의 내부 상태를 확인해야 하며, 일시적으로 사용할 수 없는 외부 종속성(예: 데이터베이스 연결)을 확인해서는 안 됩니다. 외부 종속성이 다운되면 재시작 루프에 빠질 수 있습니다.
   * 정상적인 종료: 쿠버네티스가 컨테이너를 종료할 때 애플리케이션이 SIGTERM 신호를 정상적으로 처리하여 깔끔하게 종료될 수 있도록 합니다.
   * 로깅: 프로브의 출력이 로깅되도록 하여 실패 시 디버깅할 수 있도록 합니다.

  MariaDB 예시에서는 mariadb-admin ping을 사용하는 ExecAction을 사용했습니다. 이 명령은 MariaDB 서버가 응답하는지 확인하며, 이는 서버의 활성 상태를 나타내는 좋은 지표입니다.

### Readiness Probe (준비 프로브)

readinessProbe는 쿠버네티스에서 파드 내 컨테이너의 상태를 진단하는 프로브입니다. 주된 목적은 컨테이너가 트래픽을 처리할 준비가 되었는지 확인하는 것입니다. 만약 readiness probe가 실패하면, 쿠버네티스는 해당 파드로 트래픽을 보내는 것을 중단합니다.

  자세한 설명은 다음과 같습니다:

  목적:
  readiness probe의 주요 목표는 컨테이너가 서비스의 로드 밸런서 풀에 추가되기 전에 완전히 초기화되어 들어오는 요청을 처리할 수 있는지 확인하는 것입니다. 이는 시작 시간이 필요한 애플리케이션(예: 데이터 로드, 데이터베이스 연결 설정, 캐시 워밍업)에 매우 중요합니다. readiness probe가 없으면 파드가 실제로 준비되기 전에 트래픽을 받기 시작하여 요청 실패 및 사용자 경험 저하로 이어질 수 있습니다.

  작동 방식:
  쿠버네티스는 구성된 readiness probe를 컨테이너에 주기적으로 실행합니다.
   * 프로브가 성공적인 상태(예: HTTP 200, 명령 종료 코드 0)를 반환하면 컨테이너는 준비된 것으로 간주됩니다.
   * 실패 상태(예: HTTP 500, 0이 아닌 명령 종료 코드)를 반환하면 컨테이너는 준비되지 않은 것으로 간주됩니다.

  실패 시 조치:
  readiness probe가 실패하면:
   1. 쿠버네티스는 파드의 레이블과 일치하는 모든 서비스의 엔드포인트에서 해당 파드의 IP 주소를 제거합니다. 이는 이 파드로 새로운 트래픽이 라우팅되지 않음을 의미합니다.
   2. 컨테이너는 계속 실행됩니다. 쿠버네티스는 readiness probe가 실패하더라도 컨테이너를 재시작하지 않습니다. 단순히 프로브가 다시 성공할 때까지 들어오는 트래픽으로부터 컨테이너를 격리합니다.

  readiness probe의 종류:
  liveness probe와 마찬가지로 readiness probe는 세 가지 주요 유형을 지원합니다:

   1. `ExecAction` (명령 프로브):
       * 컨테이너 내부에서 지정된 명령을 실행합니다.
       * 명령이 상태 코드 0으로 종료되면 프로브는 성공으로 간주됩니다.
       * 예시: command: ["/bin/check-app-ready.sh"] (데이터베이스 연결, 캐시 상태 등을 확인하는 스크립트). MariaDB 예시에서 사용한 방식입니다.

   2. `HTTPGetAction` (HTTP 프로브):
       * 지정된 IP 주소, 포트 및 경로에 HTTP GET 요청을 수행합니다.
       * HTTP 응답 코드가 2xx 또는 3xx이면 프로브는 성공으로 간주됩니다.
       * 예시: httpGet: { path: /readyz, port: 8080 }

   3. `TCPSocketAction` (TCP 프로브):
       * 지정된 포트에서 TCP 소켓을 열려고 시도합니다.
       * TCP 연결이 설정되면 프로브는 성공으로 간주됩니다.
       * 예시: tcpSocket: { port: 8080 } (포트가 열려 있고 수신 대기 중인지 확인).

  주요 매개변수:
  readiness probe는 liveness probe와 많은 매개변수를 공유합니다:

   * `initialDelaySeconds`: (선택 사항) 컨테이너가 시작된 후 readiness probe가 시작되기까지 기다리는 시간(초)입니다.
   * `periodSeconds`: (선택 사항) 프로브를 수행하는 빈도(초)입니다. 기본값은 10초입니다.
   * `timeoutSeconds`: (선택 사항) 프로브가 타임아웃되는 시간(초)입니다. 기본값은 1초입니다.
   * `successThreshold`: (선택 사항) 프로브가 실패한 후 성공으로 간주되기 위한 최소 연속 성공 횟수입니다. 기본값은 1입니다.
   * `failureThreshold`: (선택 사항) 프로브가 실패로 간주되어 파드가 서비스에서 제거되기 위한 최소 연속 실패 횟수입니다. 기본값은 3입니다.

  모범 사례 및 고려 사항:

   * Liveness와의 구분:
       * Liveness: 애플리케이션이 살아있는가? 그렇지 않다면 재시작하라.
       * Readiness: 애플리케이션이 트래픽을 처리할 준비가 되었는가? 그렇지 않다면 트래픽을 보내지 마라.
   * 시작 시간: initialDelaySeconds를 사용하여 애플리케이션이 프로브가 확인을 시작하기 전에 완전히 초기화될 충분한 시간을 줍니다.
   * 외부 종속성: readiness probe는 애플리케이션이 올바르게 작동하는 데 필요한 외부 종속성(예: 데이터베이스 연결,메시지 큐, 외부 API)을 확인하는 데 자주 사용됩니다. 중요한 종속성이 다운되면 애플리케이션은 준비되지 않은 것으로 보고해야 합니다.
   * 점진적 성능 저하: 애플리케이션이 저하된 상태(예: 중요하지 않은 외부 서비스 없이)에서도 작동할 수 있다면, readiness probe는 이를 반영해야 합니다.
   * 빠르고 정확하게: 프로브는 불필요하게 트래픽을 지연시키지 않을 만큼 빨라야 하지만, 애플리케이션의 준비 상태를 정확하게 반영할 만큼 정확해야 합니다.

  MariaDB 예시에서는 mariadb-admin ping을 사용하는 ExecAction을 사용했습니다. 이는 좋은 liveness 검사이지만, readiness의 경우 데이터베이스가 완전히 초기화되어 실제 쿼리에 대한 연결을 수락하는지 확인하는 더 포괄적인 검사가 필요할 수 있습니다. 그러나 간단한 MariaDB 인스턴스의 경우 ping으로도 충분한 경우가 많습니다.


### Startup Probe (시작 프로브)

startupProbe는 쿠버네티스에서 컨테이너 내의 애플리케이션이 성공적으로 시작되었는지 확인하는 데 사용되는 특별한 유형의 프로브입니다. 특히 시작 시간이 긴 애플리케이션(예: 대규모 데이터베이스 초기화, 복잡한 캐시 로딩, 레거시 애플리케이션)에 매우 유용합니다.

  주요 목적:

  startupProbe의 주된 목적은 애플리케이션이 완전히 시작될 때까지 livenessProbe와 readinessProbe가 간섭하는 것을 방지하는 것입니다. 시작 시간이 긴 애플리케이션의 경우, livenessProbe나 readinessProbe가 initialDelaySeconds를 충분히 길게 설정하지 않으면 애플리케이션이 완전히 시작되기도 전에 프로브가 실패하여 컨테이너가 불필요하게 재시작되는 문제가 발생할 수 있습니다.

  작동 방식:

   1. 초기 단계: 컨테이너가 시작되면 startupProbe만 활성화됩니다. 이 단계에서는 livenessProbe와 readinessProbe는 비활성화됩니다.
   2. 시작 완료 확인: startupProbe는 애플리케이션이 완전히 시작되고 준비될 때까지 계속 실행됩니다.
   3. 성공 시: startupProbe가 성공하면, 쿠버네티스는 livenessProbe와 readinessProbe를 활성화하고, 이후 컨테이너의 상태 관리는 이 두 프로브에 의해 이루어집니다.
   4. 실패 시: startupProbe가 failureThreshold에 도달할 때까지 계속 실패하면, 쿠버네티스는 해당 컨테이너를 종료하고 재시작합니다. 이는 애플리케이션이 지정된 시간 내에 시작되지 못했음을 의미합니다.

  `livenessProbe` 및 `readinessProbe`와의 상호작용:

   * `initialDelaySeconds` 문제 해결: startupProbe를 사용하면 livenessProbe와 readinessProbe의 initialDelaySeconds를 짧게 설정할 수 있습니다. 애플리케이션의 실제 시작 시간과 관계없이 startupProbe가 시작 완료를 보장하기 때문입니다.
   * 불필요한 재시작 방지: 시작 시간이 긴 애플리케이션이 완전히 시작되기도 전에 livenessProbe가 실패하여 컨테이너가 재시작되는 것을 방지합니다.
   * 정확한 상태 관리: 애플리케이션이 완전히 시작된 후에만 livenessProbe와 readinessProbe가 활성화되므로, 컨테이너의 상태를 더 정확하게 관리할 수 있습니다.

  `startupProbe`의 유형:

  livenessProbe 및 readinessProbe와 동일하게 세 가지 유형의 핸들러를 지원합니다.

   1. `ExecAction` (명령 프로브): 컨테이너 내부에서 명령을 실행하고 종료 코드를 확인합니다.
   2. `HTTPGetAction` (HTTP 프로브): HTTP GET 요청을 보내고 응답 코드를 확인합니다.
   3. `TCPSocketAction` (TCP 프로브): 지정된 포트로 TCP 연결을 시도합니다.

  주요 매개변수:

  startupProbe도 다른 프로브와 유사한 매개변수를 가집니다.

   * `initialDelaySeconds`: (선택 사항) 컨테이너 시작 후 startupProbe가 시작되기까지의 초기 지연 시간.
   * `periodSeconds`: (선택 사항) 프로브를 실행하는 주기.
   * `timeoutSeconds`: (선택 사항) 프로브가 타임아웃되는 시간.
   * `successThreshold`: (선택 사항) 프로브가 성공으로 간주되기 위한 연속 성공 횟수.
   * `failureThreshold`: (선택 사항) 프로브가 실패로 간주되어 컨테이너가 재시작되기 위한 연속 실패 횟수.

  모범 사례 및 고려 사항:

   * 시작 시간 예측: startupProbe의 failureThreshold와 periodSeconds를 설정할 때 애플리케이션의 최대 시작 시간을 고려해야 합니다. periodSeconds * failureThreshold가 애플리케이션의 최대 시작 시간보다 길어야 합니다.
   * 정확한 시작 조건: startupProbe는 애플리케이션이 실제로 트래픽을 처리할 준비가 되었는지보다는 성공적으로 시작되었는지에 초점을 맞춰야 합니다. 예를 들어, 웹 서버의 경우 포트가 열리고 기본 응답을 반환하는 것만으로도 충분할 수 있습니다.
   * 다른 프로브와의 조화: startupProbe가 성공한 후 livenessProbe와 readinessProbe가 즉시 활성화되므로, 이들의 initialDelaySeconds는 짧게 설정하는 것이 좋습니다.
   * 불필요한 사용 자제: 시작 시간이 짧은 애플리케이션에는 startupProbe가 필요하지 않을 수 있습니다.
     initialDelaySeconds만으로 충분하다면 사용하지 않는 것이 좋습니다.
