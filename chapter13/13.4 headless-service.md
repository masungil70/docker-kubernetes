1. Headless Service란 무엇인가?

Headless Service는 이름 그대로 "머리(Head)가 없는" 서비스입니다. 여기서 '머리'란 서비스의 고정된 가상 IP 주소, 즉 ClusterIP를 의미합니다.

일반적인 쿠버네티스 서비스(ClusterIP 타입)와 비교하면 그 차이점이 명확해집니다.

일반적인 서비스 (ClusterIP Service)

* 목적: 여러 Pod에 대한 단일 진입점(Single Entrypoint) 및 로드 밸런싱 제공.
* 동작:
    1. 고유한 가상 IP 주소(ClusterIP)를 할당받습니다.
    2. 서비스의 DNS 이름 (my-service.default.svc.cluster.local)은 이 단일 ClusterIP로 해석(resolve)됩니다.
    3. 클라이언트가 이 ClusterIP로 요청을 보내면, 서비스는 요청을 자신에게 연결된 여러 Pod 중 하나에게 분배(로드 밸런싱)합니다.
    4. 클라이언트는 개별 Pod의 IP 주소를 전혀 알 필요가 없습니다.

* 비유: 회사의 대표 전화번호. 전화를 걸면 교환원(서비스)이 받아서 담당 직원(Pod) 중 한 명에게 연결해 줍니다. 당신은 직원의 직통 번호(Pod IP)를 몰라도 됩니다.

YAML 예시 (일반 서비스):
```
vi my-service.yaml

apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  clusterIP: 10.100.20.15 # 자동으로 할당되는 가상 IP
  selector:
    app: my-web
  ports:
  - port: 80
```
Headless Service

* 목적: Pod에 대한 서비스 디스커버리(Service Discovery). 즉, Pod들을 묶어서 관리하되, 개별 Pod에 직접 접근할 수 있도록 각 Pod의 실제 IP 주소를 알려주는 것.
* 동작:
    1. spec.clusterIP 필드를 None으로 설정하여 생성합니다.
    2. ClusterIP를 할당받지 않습니다. (로드 밸런싱 기능 없음)
    3. 서비스의 DNS 이름 (my-headless-svc)을 조회하면, 단일 IP가 아닌 서비스에 연결된 모든 Pod들의 실제 IP 주소 목록이 반환됩니다.

* 비유: 회사의 내선 번호부. 번호부를 조회하면 모든 직원의 직통 번호(Pod IP) 목록을 얻게 되고, 당신이 직접 원하는 직원에게 전화를 걸 수 있습니다.

YAML 예시:
```
vi my-headless-svc.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-headless-svc
spec:
  clusterIP: None # 이 부분이 Headless Service의 핵심입니다.
  selector:
    app: my-web
  ports:
  - port: 80
```

2. Headless Service는 어떤 상황에서 사용하는가?

Headless Service는 로드 밸런싱이 필요 없고, 대신 개별 Pod를 식별하여 직접 통신해야 하는 경우에 사용됩니다.

사용 사례 1: StatefulSets (가장 대표적인 사례)

* 앞선 설명처럼, StatefulSet은 각 Pod에 pod-0.service.ns, pod-1.service.ns 와 같은 고유하고 안정적인 네트워크 식별자를 제공해야 합니다.
* Headless Service는 바로 이 개별 Pod의 DNS 이름을 생성하는 기반이 됩니다. StatefulSet이 Headless Service와 연결되면, Kubernetes DNS 시스템은 Headless Service에 속한 각 Pod에 대해 고유한 A 레코드(DNS 주소)를 만들어 줍니다.
* 예시: 데이터베이스 클러스터에서 복제본(Replica) Pod가 마스터(Master) Pod(master-0.db-svc)를 정확히 찾아가야 할 때, 로드 밸런서가 중간에 끼어들면 안 됩니다. Headless Service를 통해 마스터 Pod의 실제 IP를 직접 알아내어 통신해야 합니다.

사용 사례 2: 분산 시스템의 피어(Peer) 디스커버리

* Cassandra, MongoDB, Zookeeper, etcd 등 분산 데이터베이스나 코디네이션 시스템은 각 노드(Pod)가 클러스터를 형성하기 위해 다른 모든 노드의 존재를 알고 직접 통신해야 합니다.
* 새로운 Pod가 클러스터에 참여할 때, Headless Service의 DNS를 조회하여 현재 클러스터에 참여 중인 다른 모든 Pod들의 IP 목록을 한 번에 받아올 수 있습니다. 이를 통해 클러스터 멤버 목록을 구성하고 서로 통신을 시작합니다.

사용 사례 3: 클라이언트 사이드 로드 밸런싱 (Client-Side Load Balancing)

* 쿠버네티스의 내장 로드 밸런싱(kube-proxy 기반) 대신, 클라이언트 애플리케이션이 직접 로드 밸런싱 로직을 수행하고 싶을 때 사용합니다.
* 동작 방식:
    1. 클라이언트는 Headless Service에 DNS 조회를 요청하여 모든 백엔드 Pod의 IP 목록을 얻습니다.
    2. 클라이언트는 이 IP 목록을 가지고 자체 로직(예: Round Robin, Least Connections 등)에 따라 연결할 Pod를 직접 선택합니다.
* 장점: 서비스 프록시를 거치지 않아 네트워크 홉(hop)이 줄어들고, 더 정교한 로드 밸런싱 전략을 구사할 수 있습니다.

---

요약 비교


|특징|일반적인 서비스 (ClusterIP)|Headless Service|
|---|---|---|
| `clusterIP`| 자동으로 가상 IP 주소 할당| None|
| 주요 목적 | 로드 밸런싱, 단일 진입점 |서비스 디스커버리, 직접 접근|
| DNS 조회 결과|서비스의 가상 IP (1개)| 서비스에 속한 모든 Pod의 실제 IP (여러 개)|
| 통신 방식|클라이언트 → 서비스(VIP) → Pod|클라이언트 → Pod (직접)|
| 대표 사용 사례 | Stateless 웹 서버, API 서버|StatefulSets, 분산 시스템, 클라이언트 사이드 로드 밸런싱 |


결론적으로, "여러 Pod들을 논리적으로 묶고 싶지만, 그 중 하나와 랜덤하게 통신하는 것이 아니라, 특정 Pod 또는 모든 Pod와
개별적으로 직접 통신해야 할 때" Headless Service를 사용합니다.
