### Metrics Server

 1. Metrics Server란 무엇인가?

  Metrics Server는 Kubernetes 클러스터의 핵심 모니터링 구성 요소 중 하나입니다.

  한마디로 "클러스터 전체의 리소스 사용량(CPU, 메모리)을 수집하여 집계하는 경량(lightweight) 서버"입니다.

  주요 역할은 클러스터 내의 모든 노드(Node)와 파드(Pod)가 현재 얼마나 많은 CPU와 메모리를 사용하고 있는지를 알려주는 것입니다.

  2. 왜 필요한가? (핵심 목적)

  Metrics Server의 가장 중요한 존재 이유는 Kubernetes의 자동 확장(Autoscaling) 기능을 지원하기 위함입니다.

   * Horizontal Pod Autoscaler (HPA): "파드의 CPU 사용량이 80%를 넘으면 파드 개수를 2개에서 3개로 늘려라" 와 같은 규칙을 HPA에 설정할 수 있습니다. 이때 HPA는 주기적으로 Metrics Server에게 "파드들의 현재 CPU 사용량이 얼마야?" 라고 물어보고, 그 값을 기준으로 파드의 개수를 조절합니다.
   * Vertical Pod Autoscaler (VPA): "파드가 지속적으로 메모리를 1GB 이상 사용하면, 다음 배포 시에는 메모리 요청(request)량을 1.2GB로 늘려라" 와 같이 파드 자체의 리소스 할당량을 조절할 때, VPA가 Metrics Server의 데이터를 참조합니다.
   * `kubectl top` 명령어: 개발자가 터미널에서 kubectl top node 또는 kubectl top pod 명령어를 실행하면, 바로 이 Metrics Server가 수집한 실시간 리소스 사용량을 보여주는 것입니다.

  Metrics Server가 없다면 HPA나 kubectl top 명령어는 동작하지 않습니다.

  3. 어떻게 동작하는가?

   1. 데이터 수집: 클러스터의 각 노드에는 kubelet이라는 에이전트가 실행됩니다. 이 kubelet 안에는 cAdvisor가 내장되어 있습니다. Metrics Server는 각 노드의 kubelet으로부터 주기적으로 CPU, 메모리 사용량 데이터를 가져옵니다.
   2. 데이터 집계: 모든 노드로부터 수집한 데이터를 취합하여 메모리 내에 저장합니다.
   3. API 제공: 수집한 데이터를 Kubernetes의 공식 Metrics API (`metrics.k8s.io`) 를 통해 제공합니다. HPA나 kubectl 같은 다른 구성 요소들은 이 API를 통해 Metrics Server에게 데이터를 요청하는 것입니다.

  [ 데이터 흐름 ]
  cAdvisor (각 노드) → kubelet (각 노드) → Metrics Server (클러스터 전체) → HPA, kubectl 등

  4. cAdvisor와의 차이점

  | 구분 |cAdvisor| Metrics Server|
  |------|--------|--------------|
  | 역할 | 상세 데이터 수집기|요약 데이터 집계 및 제공자 |
  | 범위 | 컨테이너가 실행되는 단일 노드| Kubernetes 클러스터 전체|
  |수집 메트릭 | CPU, 메모리, 네트워크, 파일시스템 등 매우 상세하고 다양한 정보 | CPU, 메모리 핵심 리소스 정보만 수집|
  | 데이터 저장 | 단기(몇 분) 데이터만 메모리에 저장 | 더 짧은 단기 데이터만 메모리에 저장 (장기 보관 X) |
  | 주요 사용자 | 개발자/엔지니어의 직접적인 분석 (UI 통해) | Kubernetes 내부 컴포넌트 (HPA 등), kubectl top|
  | 자체 UI | 있음| 없음 (API로만 데이터 제공)|
  
  결론적으로, cAdvisor는 "현미경"처럼 하나의 노드를 상세하게 들여다보는 도구이고, Metrics Server는 "망원경"처럼 클러스터 전체의 핵심 자원 현황을 멀리서 조망하는 역할을 합니다.

  Kubernetes 클러스터에 Metrics Server를 설치하고 사용하는 방법

  1단계: 사전 준비

  Metrics Server를 설치하기 전, 아래 두 가지가 반드시 준비되어 있어야 합니다.

   1. 실행 중인 Kubernetes 클러스터:
       * Minikube, Kind, Docker Desktop에 포함된 Kubernetes 등 로컬 개발용 클러스터
       * GKE(Google), EKS(Amazon), AKS(Azure) 등 클라우드 기반의 관리형 클러스터
   2. 클러스터에 연결된 `kubectl` CLI:
       * 터미널에서 kubectl get nodes 명령어를 실행했을 때, 클러스터의 노드 목록이 정상적으로 보여야 합니다.

  2단계: Metrics Server 설치 및 확인

  2.1. 설치 명령어 실행

  Metrics Server는 공식 YAML 파일을 kubectl apply 명령어로 실행하여 간단하게 설치할 수 있습니다.
  이 YAML 파일 안에는 Metrics Server 실행에 필요한 모든 리소스(Deployment, Service, RBAC 등)가
  정의되어 있습니다.

  아래 명령어를 터미널에 입력하세요.
```
   kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```
  이 명령어는 Metrics Server 컴포넌트들을 kube-system 네임스페이스에 설치합니다.

  2.2. 설치 확인

  설치 명령 실행 후, Metrics Server 파드가 정상적으로 실행되고 있는지 확인해야 합니다.
```
kubectl get pods -n kube-system | grep metrics-server
```
  [실행 예시]
```
   NAME                              READY   STATUS    RESTARTS   AGE
   metrics-server-577c96f8d4-z5jxp   1/1     Running   0          2m
```
  STATUS가 Running이고 READY가 1/1이 될 때까지 1~2분 정도 소요될 수 있습니다.

  2.3. (중요) 로컬 클러스터 추가 설정

  Minikube, Kind, K3s 등 로컬 개발용 클러스터를 사용 중이라면, Metrics Server가 각 노드의
  Kubelet과 통신할 때 TLS 인증서 문제로 실패할 수 있습니다. 이 경우, 아래 패치 명령어를 실행하여
  TLS 검증을 건너뛰도록 설정해야 합니다.
```
kubectl patch deployment metrics-server -n kube-system --type='json' -p='[{"op": "add", "path": "/spec/template/spec/containers/0/args/-", "value": "--kubelet-insecure-tls"}]'
```
  > 경고: 이 설정은 TLS 보안 검증을 비활성화하므로 개발 및 테스트 환경에서만 사용해야 합니다. 실제 운영(Production) 환경에서는 사용하지 마세요.

  3단계: Metrics Server 사용법

  설치가 완료되고 Metrics Server가 데이터를 수집하기 시작하면(약 1~2분 소요), kubectl top
  명령어를 사용할 수 있게 됩니다.

  3.1. 노드(Node) 리소스 사용량 확인

  클러스터에 있는 각 노드의 현재 CPU 및 메모리 사용량을 확인합니다.
```
kubectl top node
```
  [결과 예시]
```
  NAME       CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
  minikube   315m         15%    1241Mi          32%
```
   * CPU(cores): 사용된 CPU 양 (m = milli-cores, 1000m = 1 core)
   * MEMORY(bytes): 사용된 메모리 양 (Mi = Mebibytes)

  3.2. 파드(Pod) 리소스 사용량 확인

  실행 중인 각 파드의 현재 CPU 및 메모리 사용량을 확인합니다.

  1) 현재 네임스페이스의 파드 확인
```  
kubectl top pod
```

  2) 모든 네임스페이스의 파드 확인 (`-A` 또는 `--all-namespaces` 옵션)
```
kubectl top pod -A
```

  [결과 예시]
```
NAMESPACE     NAME                               CPU(cores)   MEMORY(bytes)
kube-system   coredns-5dd5756b68-v2z5x            4m           12Mi
kube-system   etcd-minikube                       25m          49Mi
kube-system   kube-apiserver-minikube             69m          270Mi
kube-system   kube-controller-manager-minikube    31m          53Mi
kube-system   kube-proxy-k78jh                    1m           18Mi
kube-system   kube-scheduler-minikube             7m           23Mi
kube-system   metrics-server-577c96f8d4-z5jxp     3m           18Mi
kube-system   storage-provisioner                 2m           16Mi
```
  만약 kubectl top 명령어 실행 시 "Metrics not available yet" 메시지가 나온다면, Metrics Server가
  아직 데이터를 수집 중이거나 통신에 문제가 있는 것이니 잠시 후 다시 시도해 보세요.

  4단계: 다음 단계 (HPA와 연동)

  Metrics Server와 HPA(Horizontal Pod Autoscaler)를 사용하여 CPU 사용량에 따라 파드가 자동으로 확장(scale-out)되는 전체 과정을 테스트할 수 있습니다.

  이 예제는 3개의 YAML 파일로 구성됩니다.
   1. Deployment: CPU 부하를 유발하는 웹 애플리케이션을 배포합니다.
   2. Service: 배포된 애플리케이션에 외부에서 접근할 수 있도록 경로를 만들어줍니다.
   3. HPA: 애플리케이션의 CPU 사용량을 모니터링하여 자동으로 파드 개수를 조절합니다.

  1단계: 예제 파일 생성

  아래 3개의 파일을 생성하겠습니다.

  1.1. Deployment (deployment.yaml)
  Kubernetes 공식 HPA 테스트용 이미지(k8s.gcr.io/hpa-example)를 사용합니다. 이 컨테이너는 요청을 받으면 CPU를 많이 소모하는 연산을 수행합니다.

  가장 중요한 부분은 resources.requests.cpu: "200m" 입니다. HPA는 이 요청(request)량 대비 실제 사용량의 비율을 계산하여 확장 여부를 결정합니다. 즉, targetCPUUtilizationPercentage: 50 이라면, 파드의 CPU 사용량이 요청량의 50%(여기서는 100m)를 초과하면 확장을 시작합니다.

```
vi deployment.yaml

# --- Deployment --- #
# apiVersion: 쿠버네티스 API 버전. apps/v1은 Deployment, ReplicaSet, StatefulSet 등을 관리합니다.
apiVersion: apps/v1
# kind: 리소스의 종류. 여기서는 'Deployment'를 생성합니다.
kind: Deployment
# metadata: 이름, 레이블 등 리소스를 식별하기 위한 정보입니다.
metadata:
  name: php-apache # 이 Deployment의 고유한 이름
# spec: 리소스의 상세한 상태를 정의하는 부분입니다.
spec:
  # selector: 이 Deployment가 관리할 파드를 찾는 방법을 정의합니다.
  selector:
    # matchLabels: 아래 레이블을 가진 파드들을 자신의 소속으로 인식합니다.
    matchLabels:
      app: php-apache
  # replicas: 초기에 실행할 파드의 수. HPA에 의해 이 값은 동적으로 변경됩니다.
  replicas: 1
  # template: Deployment가 파드를 생성할 때 사용할 '설계도' 또는 '템플릿'입니다.
  template:
    metadata:
      # labels: 생성될 파드에 adjf될 레이블. 위의 selector와 일치해야 합니다.
      labels:
        app: php-apache
    # spec: 파드의 상세 스펙을 정의합니다.
    spec:
      # containers: 파드 내에서 실행될 컨테이너 목록입니다.
      containers:
      - name: php-apache # 컨테이너의 이름
        # image: 컨테이너를 생성할 도커 이미지
        image: k8s.gcr.io/hpa-example
        # ports: 컨테이너가 외부에 노출할 포트 정보입니다.
        ports:
        - containerPort: 80 # 컨테이너 내부에서 80번 포트를 사용
        # resources: 컨테이너가 사용할 리소스(CPU, 메모리)의 양을 정의합니다.
        resources:
          # requests: 컨테이너에 '최소한' 보장해 주어야 하는 리소스 양입니다.
          # HPA는 바로 이 'requests' 값을 기준으로 사용률을 계산하므로 매우 중요합니다.
          requests:
            cpu: "200m" # 200m = 0.2 코어. 이 파드는 최소 0.2개의 CPU 코어를 요청합니다.
```

✦ 1.2. Service (service.yaml)
  배포된 php-apache 파드에 접근할 수 있도록 LoadBalancer 타입의 서비스를 생성합니다.
```
vi service.yaml

# --- Service --- #
apiVersion: v1 # Service는 핵심(core) API 그룹에 속하므로 v1을 사용합니다.
kind: Service # 리소스의 종류는 'Service' 입니다.
metadata:
  name: php-apache # 이 Service의 고유한 이름
# spec: Service의 상세 스펙을 정의합니다.
spec:
  # selector: 이 Service가 트래픽을 전달할 대상 파드를 선택합니다.
  # 아래 레이블을 가진 파드들이 이 Service의 대상이 됩니다. (deployment.yaml의 파드 레이블과 일치해야 함)
  selector:
    app: php-apache
  # ports: 서비스가 노출할 포트를 정의합니다.
  ports:
  - protocol: TCP # 사용할 프로토콜
    port: 80 # 서비스 자체가 노출될 포트
    # targetPort는 생략되었으며, 이 경우 자동으로 'port'와 동일한 값(80)으로 설정됩니다.
  # type: 서비스의 종류를 정의합니다.
  type: NodePort
```

✦ 1.3. HorizontalPodAutoscaler (hpa.yaml)

```
vi hpa.yaml

# --- HorizontalPodAutoscaler --- #
# apiVersion: autoscaling/v1은 CPU 기반의 스케일링만 지원하는 기본 버전입니다.
# (메모리나 커스텀 메트릭을 사용하려면 autoscaling/v2를 사용해야 합니다.)
apiVersion: autoscaling/v1
kind: HorizontalPodAutoscaler # 리소스의 종류는 'HPA' 입니다.
metadata:
  name: php-apache # 이 HPA의 고유한 이름
# spec: HPA의 동작 방식을 상세하게 정의합니다.
spec:
  # scaleTargetRef: 스케일링(확장/축소)을 적용할 대상을 지정합니다.
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache # 'php-apache'라는 이름의 Deployment를 대상으로 함
  
  # minReplicas: 파드의 최소 개수. 아무리 부하가 없어도 이 개수는 유지됩니다.
  minReplicas: 1
  # maxReplicas: 파드의 최대 개수. 아무리 부하가 많아도 이 개수를 초과하여 확장되지 않습니다.
  maxReplicas: 10

  # targetCPUUtilizationPercentage: 스케일링의 기준이 되는 목표 CPU 사용률입니다.
  # 파드들의 평균 CPU 사용률이 이 값을 초과하면 파드 개수를 늘리고, 낮아지면 줄입니다.
  # 사용률 = (실제 CPU 사용량 / 파드에 요청된 CPU 양(requests.cpu)) * 100
  targetCPUUtilizationPercentage: 50

```
  php-apache 디플로이먼트를 대상으로 하는 HPA를 생성합니다. 평균 CPU 사용률이 50%를 넘으면 파드
  개수를 1개부터 최대 10개까지 늘립니다. (80% 이상을 확실히 보기 위해 임계값을 50%로 설정)

✦ 2단계: Kubernetes에 리소스 배포

  이제 생성한 3개의 YAML 파일을 클러스터에 적용합니다.
```
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f hpa.yaml
```

  3단계: 부하 발생시키기

  이제 애플리케이션에 지속적인 부하를 주어 CPU 사용량을 높여야 합니다.

  1. 서비스 IP 확인

  먼저 php-apache 서비스의 Node IP를 확인합니다.

```
ip addr
```

  2. 부하 발생용 컨테이너 실행

  가장 간단한 방법은, 부하를 발생시키기 위한 별도의 컨테이너를 하나 실행하는 것입니다. 아래 명령어를 실행하면 while 루프를 통해 php-apache 서비스에 무한정 요청을 보내는 컨테이너가 생성됩니다.

. 부하 발생용 Pod YAML 파일 생성

  아래 load-generator.yaml 파일은 busybox 이미지를 사용하여, php-apache 서비스에 0.01초마다 계속
  요청을 보내는 간단한 파드를 생성합니다.

```
vi load-generator.yaml

# --- Load Generator Pod --- #
apiVersion: v1
kind: Pod # Deployment가 아닌 단일 Pod를 생성합니다. 이 작업만 하고 삭제될 임시 파드입니다.
metadata:
  name: load-generator # 파드의 이름
spec:
  containers:
  - name: load-generator-container # 컨테이너의 이름
    image: busybox # 경량화된 기본 유닉스 도구가 포함된 이미지
    
    # 아래 command와 args는 컨테이너가 시작될 때 실행할 명령어를 정의합니다.
    command: ["/bin/sh"]
    args: 
    - "-c"
    # 'php-apache'는 Service의 이름입니다. 쿠버네티스 내부 DNS가 이 이름을
    # 해당 서비스의 IP로 자동 변환해 줍니다.
    - "while sleep 0.01; do wget -q -O- http://php-apache; done"

```

✦ 2. 사용 방법

  이제 이 YAML 파일을 사용하여 부하 테스트를 시작하고 중지할 수 있습니다.

  부하 테스트 시작

  아래 명령어를 실행하여 load-generator 파드를 클러스터에 배포합니다. 파드가 생성되는 즉시 부하가
  발생하기 시작합니다.

```
kubectl apply -f load-generator.yaml
```

  이제 이전과 동일하게 새 터미널을 열고 HPA의 상태를 관찰하여 파드가 확장되는 것을 확인하세요.
```
kubectl get hpa php-apache -w
```
  부하 테스트 중지

  부하를 멈추고 싶을 때는, 생성했던 load-generator 파드를 삭제하면 됩니다.
```
kubectl delete pod load-generator
```

  파드가 삭제되면 php-apache로 가는 요청이 즉시 중단되고, 몇 분 후 HPA가 파드 개수를 다시
  최소치로 줄이는 것을 확인할 수 있습니다.


Metrics Server의 동작 원리를 단계별로 설명해 드리겠습니다.

쿠버네티스 클러스터를 하나의 '학교'라고 상상해 보세요.

  ---

  1단계: 교실(Node)과 학생들(Pod)

   * 이 학교에는 여러 개의 교실(서버 컴퓨터, Node)이 있습니다.
   * 각 교실 안에는 여러 학생(애플리케이션, Pod)들이 앉아서 열심히 공부(작업)를 하고 있습니다.

  2단계: 모든 것을 아는 담임 선생님 (Kubelet)

   * 각 교실에는 담임 선생님(Kubelet)이 한 명씩 있습니다.
   * 담임 선생님은 자기 반 학생(Pod)들의 상태를 속속들이 알고 있습니다. 어떤 학생이 얼마나 집중해서
     공부하는지(CPU 사용량), 책상을 넓게 쓰는지(메모리 사용량) 등을 항상 파악하고 있습니다.
       * (기술 노트: 담임 선생님은 학생 책상에 붙어있는 'cAdvisor'라는 건강 기록부를 보고 상태를 파악합니다.)

  3단계: '전교 회장'의 등장 (Metrics Server)

   * 어느 날, 교장 선생님(HPA, 자동 확장 기능)이 이런 생각을 합니다. "전교생의 평균 집중도가 80%를 넘으면 교실을 하나 더 만들어줘야겠다! 그런데 내가 일일이 모든 교실을 돌아다니며 물어볼 순 없지..."
   * 그래서 교장 선생님은 '전교 회장(Metrics Server)'을 한 명 임명합니다.
   * 전교 회장의 임무는 단 하나입니다. 모든 교실을 돌아다니며 담임 선생님에게 딱 두 가지만 물어보는 것입니다.

  4단계: 전교 회장의 '설문조사' (데이터 수집)

   * 전교 회장(Metrics Server)은 주기적으로(예: 1분마다) 모든 교실을 방문합니다.
   * 그리고 각 교실의 담임 선생님(Kubelet)에게 가서 묻습니다.
      > "선생님 반 학생들의 현재 '공부 집중도(CPU)'와 '책상 사용량(메모리)' 목록을 주세요."
   * 담임 선생님은 자기가 파악하고 있던 학생들의 정보를 전교 회장에게 넘겨줍니다.
   * 전교 회장은 이렇게 모든 반에서 받은 정보를 취합하여 최신 상태로 자신의 수첩에 기록해 둡니다.
     (오래된 정보는 버리고 항상 최신 정보만 가집니다.)

  5단계: 교장 선생님의 '질문' (데이터 제공)

   * 이제 교장 선생님(HPA)은 학생들의 상태가 궁금할 때, 모든 교실을 돌아다닐 필요가 없습니다.
   * 그저 전교 회장(Metrics Server)에게 가서 물어보기만 하면 됩니다.
      > "전교생 평균 집중도가 몇 퍼센트인가?"
      > "A반의 '김파드' 학생은 책상을 얼마나 쓰고 있나?"
   * 그러면 전교 회장은 자신의 수첩을 보고 바로바로 대답해 줍니다. 이 정보를 바탕으로 교장 선생님은
     교실을 늘릴지 말지(오토스케일링) 결정할 수 있게 됩니다.
   * 우리가 터미널에 kubectl top pod 라고 치는 것도, 교장 선생님처럼 전교 회장에게 가서 물어보는
     것과 똑같은 행동입니다.

  ---

   * 담임 선생님 (Kubelet): 자기 반 학생(Pod)들의 모든 것을 알고 있음.
   * 전교 회장 (Metrics Server): 모든 반을 돌며 오직 CPU, 메모리 정보만 물어봐서 최신 목록을 가지고 있음.
   * 교장 선생님 (HPA): 전교 회장에게만 가서 요약된 정보를 받아 중요한 결정을 함.

  이처럼 Metrics Server는 클러스터 전체의 핵심 성능 지표(CPU, 메모리)를 모아주는 '전교 회장' 같은
  역할을 하여, HPA와 같은 다른 기능들이 효율적으로 동작할 수 있도록 돕는 아주 중요한 존재입니다.


### kube-state-metrics 란 ?

  1. kube-state-metrics란 무엇인가?

  한마디로 "쿠버네티스 클러스터의 상태 정보(State)를 메트릭(숫자 데이터)으로 변환해 주는 변환기" 입니다.

  kube-state-metrics는 리소스 사용량(CPU/메모리)을 알려주는 것이 아닙니다. 대신, 쿠버네티스 오브젝트(Pod, Deployment, Node 등)들의 상태, 설정, 개수와 같은 '행정 정보'를 숫자 형태로 제공합니다.

  다시 학교 비유를 들어보겠습니다.
   * Metrics Server가 학생들의 '공부 집중도(CPU)'와 '책상 사용량(메모리)'을 알려주는 '전교 회장'이었다면,
   * `kube-state-metrics`는 학교의 모든 '행정 정보'를 관리하는 '교무실'과 같습니다.

  교무실은 학생이 얼마나 열심히 공부하는지(CPU)는 모르지만, 아래와 같은 정보들을 알고 있습니다.
   * "3학년 1반에 배정된 학생 수는 총 몇 명인가?"
   * "오늘 결석한 학생은 몇 명인가?"
   * "현재 학교에 있는 총 학생 수는 몇 명인가?"
   * "고장 난 책상(비정상 노드)은 몇 개인가?"

  2. 왜 필요한가? (목적)

  kube-state-metrics는 클러스터의 '건강 상태' 와 '정상 동작 여부' 를 판단하는 데 필수적인 정보를 제공합니다. 이 정보를 통해 우리는 다음과 같은 질문에 답할 수 있습니다.

   * "Deployment에 설정한 파드 개수(replicas)와 현재 실행 중인 파드 개수가 일치하는가?"
   * "특정 사유로 인해 Pending(대기) 상태에 머물러 있는 파드는 없는가?"
   * "컨테이너가 계속 재시작(restart)되고 있는 파드는 없는가?"
   * "Job이나 CronJob이 실패하지는 않았는가?"
   * "사용 불가능한(NotReady) 노드는 없는가?"

  이러한 정보들은 CPU/메모리 사용량만으로는 알 수 없는, 클러스터의 근본적인 문제를 파악하고 알림을 설정하는 데 매우 중요합니다.

  3. 어떻게 동작하는가?

   1. API 서버 감시: kube-state-metrics는 쿠버네티스의 모든 상태 정보가 저장되는 중앙 저장소, 즉 API 서버를 계속 감시(Watch)합니다.
   2. 상태를 메트릭으로 변환: API 서버로부터 Deployment, Pod, Node 등 모든 오브젝트의 상태 정보를 읽어옵니다. 그리고 그 정보들을 Prometheus가 수집할 수 있는 텍스트 기반의 메트릭 형식으로 변환합니다.
   3. 메트릭 노출: 변환된 메트릭들을 자신의 /metrics HTTP 엔드포인트에 노출시킵니다.
   4. 데이터 미저장: kube-state-metrics는 어떠한 데이터도 자체적으로 저장하지 않습니다. 그저 API 서버의 현재 상태를 실시간으로 변환하여 보여주는 역할만 합니다.

  [ 데이터 흐름 ]
  Kubernetes API 서버 → kube-state-metrics → (스크랩) → Prometheus

  4. 어떤 메트릭을 제공하는가? (예시)

  kube-state-metrics가 제공하는 대표적인 메트릭들은 다음과 같습니다.

   * Deployment 관련
       * kube_deployment_spec_replicas: Deployment에 설정된 목표 파드 개수
       * kube_deployment_status_replicas_available: 현재 사용 가능한 파드 개수
       * 사용 예시: spec_replicas와 replicas_available 값이 다르면 배포에 문제가 있다는 알림을 보낼 수 있습니다.

   * Pod 관련
       * kube_pod_status_phase: 파드의 현재 단계 (Pending, Running, Succeeded, Failed 등)를 숫자로 표시
       * kube_pod_container_status_restarts_total: 파드 내 컨테이너가 재시작된 횟수
       * 사용 예시: 특정 파드의 재시작 횟수가 계속 증가하면 애플리케이션에 버그가 있다는 알림을 보낼 수 있습니다.

   * Node 관련
       * kube_node_status_condition: 노드의 상태 (Ready, MemoryPressure 등)가 정상인지 여부 (1=정상, 0=비정상)
       * 사용 예시: Ready 상태가 0인 노드가 발생하면 즉시 알림을 보낼 수 있습니다.

  5. 세 가지 모니터링 도구 비교

  이제 세 가지 도구의 역할이 명확히 구분됩니다.

| 구분 | cAdvisor |  Metrics Server | kube-state-metrics |
|------|------|------|------|
|주요 역할| 컨테이너 리소스 상세 측정| 리소스 사용량 요약 및 집계 │ 쿠버네티스 오브젝트 상태 변환|
|데이터 소스|컨테이너 런타임| 각 노드의 Kubelet|API 서버 |
|제공 정보|CPU, 메모리, 네트워크, 파일 I/O 등 상세 정보|CPU, 메모리 사용량|오브젝트의 개수, 상태, 설정 등 행정 정보|
|주요 사용처|단일 노드 상세 분석|HPA, kubectl top|Prometheus (클러스터 상태 모니터링 및 알림)|


  이 세 가지 도구는 경쟁 관계가 아니라, 서로 다른 정보를 제공하며 상호 보완하는 관계입니다. 보통 Prometheus가 이 세 가지(정확히는 cAdvisor와 kube-state-metrics)를 모두 수집하여 완전한 클러스터 모니터링 환경을 구축하게 됩니다.

  kube-state-metrics는 그 자체로 UI나 대시보드를 제공하지 않습니다. 대신, Prometheus 같은 모니터링 시스템이 수집해갈 수 있도록 순수한 텍스트 형식의 메트릭을 /metrics 엔드포인트에 노출하는 것이 주된 역할입니다.

  ---

  1단계: kube-state-metrics 설치

  쿠버네티스 공식 저장소에 있는 YAML 파일들을 사용하여 설치합니다. 이 파일들은 kube-state-metrics를 실행하기 위한 Deployment, Service, 그리고 API 서버에 접근하는 데 필요한 권한(ServiceAccount, RBAC)을 모두 포함하고 있습니다.

  터미널에 아래 명령어를 입력하세요.
```
kubectl apply -f https://raw.githubusercontent.com/kubernetes/kube-state-metrics/main/examples/standard/cluster-role-binding.yaml
kubectl apply -f https://raw.githubusercontent.com/kubernetes/kube-state-metrics/main/examples/standard/cluster-role.yaml
kubectl apply -f https://raw.githubusercontent.com/kubernetes/kube-state-metrics/main/examples/standard/deployment.yaml
kubectl apply -f https://raw.githubusercontent.com/kubernetes/kube-state-metrics/main/examples/standard/service-account.yaml
kubectl apply -f https://raw.githubusercontent.com/kubernetes/kube-state-metrics/main/examples/standard/service.yaml
```
  2단계: 설치 확인

  설치가 완료되면 kube-system 네임스페이스에 kube-state-metrics 파드가 실행됩니다. 아래 명령어로 확인하세요.
```
kubectl get pods -n kube-system | grep kube-state-metrics
```
  [실행 예시]
```
NAME                                  READY   STATUS    RESTARTS   AGE
kube-state-metrics-7f948f555f-5z6j8   1/1     Running   0          1m
```
  STATUS가 Running이 될 때까지 잠시 기다려 주세요.

  3단계: 메트릭 데이터에 접근하기

  kube-state-metrics 서비스는 기본적으로 클러스터 내부에서만 접근 가능합니다. 학습을 위해
  외부(내 로컬 터미널)에서 이 메트릭을 직접 확인하려면 `kubectl port-forward`를 사용하는
  것이 가장 편리합니다.

  1. `kube-state-metrics` 파드 이름 확인

  먼저 정확한 파드 이름을 변수에 저장합니다.
```
export KSM_POD_NAME=$(kubectl get pods -n kube-system -l app.kubernetes.io/name=kube-state-metrics -o jsonpath='{.items[0].metadata.name}')
```

  2. 포트 포워딩 실행

  새 터미널을 열거나 현재 터미널에서 아래 명령어를 실행하여 내 컴퓨터의 8080 포트와
  파드의 8080 포트를 연결합니다.

```
kubectl port-forward -n kube-system $KSM_POD_NAME 8080:8080
```
  [결과 예시]

```
Forwarding from 127.0.0.1:8080 -> 8080
Forwarding from [::1]:8080 -> 8080
```
  이 터미널은 메트릭을 확인하는 동안 계속 실행 상태로 두어야 합니다.

  4단계: 메트릭 확인 및 해석

  이제 kube-state-metrics가 제공하는 메트릭을 확인할 준비가 되었습니다.

  1. 전체 메트릭 확인

  새 터미널을 열고 아래 curl 명령어를 실행합니다.
```
curl http://localhost:8080/metrics
```

  엄청나게 많은 양의 텍스트가 출력될 것입니다. 이것이 바로 kube-state-metrics가 현재 클러스터의 상태를 변환하여 보여주는 메트릭 데이터입니다.

  2. 특정 메트릭 해석해보기

  이 많은 데이터 속에서 의미 있는 정보를 찾아보겠습니다. 이전에 만들었던 php-apache Deployment를 예시로 사용합니다.

   * 예시 1: Deployment의 목표 파드 개수 확인

      grep을 사용하여 php-apache Deployment의 복제본(replica) 관련 메트릭을 찾아봅니다.
```
curl -s http://localhost:8080/metrics | grep 'kube_deployment_spec_replicas{namespace="default",deployment="php-apache"}'

```
      [결과]
```
kube_deployment_spec_replicas{deployment="php-apache",namespace="default"} 1
```
  해석: php-apache Deployment는 목표 파드 개수(`spec.replicas`)가 1개로 설정되어 있다는 의미입니다.

   * 예시 2: 현재 사용 가능한 파드 개수 확인
```
curl -s http://localhost:8080/metrics | grep 'kube_deployment_status_replicas_available{deployment="php-apache"}'
```
      [결과]
```
kube_deployment_status_replicas_available{deployment="php-apache" ,namespace="default"} 1
```
      해석: 현재 사용 가능한(available) 파드의 개수가 1개라는 의미입니다. 목표 개수와 실제 사용 가능 개수가 같으므로, 이 Deployment는 현재 건강한 상태라고 판단할 수 있습니다. (만약 HPA에 의해 스케일 아웃된 상태라면 이 숫자는 더 높을 것입니다.)

   * 예시 3: 파드의 현재 상태 확인
```
# `php-apache` 라는 이름을 포함하는 파드의 상태(phase)를 찾아봅니다.
curl -s http://localhost:8080/metrics | grep 'kube_pod_status_phase' | grep 'php-apache'
```
      [결과]
```
kube_pod_status_phase{namespace="default",pod="php-apache-5fc7b55f77-abcde",phase="Running"} 1
kube_pod_status_phase{namespace="default",pod="php-apache-5fc7b55f77-abcde",phase="Failed"} 0
...
```
      해석: php-apache-로 시작하는 파드의 상태는 Running이 1(참)이고, Failed는 0(거짓)임을 의미합니다. 즉, 파드가 현재 정상적으로 실행 중이라는 것을 알 수 있습니다.

  5단계: 실제 사용 사례 (Prometheus 연동)

  지금까지의 과정은 kube-state-metrics를 이해하기 위한 방법입니다.

  실제 운영 환경에서는 Prometheus라는 모니터링 시스템이 주기적으로(예: 1분마다)
  http://kube-state-metrics.kube-system.svc.cluster.local:8080/metrics 주소로 접근하여 이
  모든 메트릭을 자동으로 수집하고 데이터베이스에 저장합니다.

  그리고 개발자는 Prometheus에 저장된 데이터를 이용하여,
   * Grafana 같은 시각화 도구로 "시간에 따른 사용 가능 파드 개수 변화" 같은 그래프를 만듭니다.
   * "Deployment의 목표 파드 수와 실제 파드 수가 5분 이상 다르면 슬랙으로 알림 보내기" 같은
     알림 규칙을 만들어 클러스터의 상태를 24시간 감시합니다.


### node-exporter 란 ?

  1. node-exporter란 무엇인가?

  한마디로 "서버 머신(하드웨어 및 운영체제)의 상태를 측정하여 메트릭으로 노출해 주는 Prometheus용 변환기" 입니다.

  node-exporter는 쿠버네티스에 대해 전혀 알지 못합니다. 파드, 디플로이먼트 같은 쿠버네티스 오브젝트에는 관심이 없습니다. 오직 자신이 실행되고 있는 서버 컴퓨터(쿠버네티스 클러스터에서는 '노드')의 물리적인 상태에만 집중합니다.

  다시 학교 비유를 들어보겠습니다.
   * kube-state-metrics가 학교의 행정 정보를 관리하는 '교무실'이었다면,
   * node-exporter는 학교 '건물' 자체의 상태를 점검하는 '시설 관리실'과 같습니다.

  시설 관리실은 반에 학생이 몇 명인지(파드 개수)는 관심 없지만, 다음과 같은 건물 자체의 상태를 점검합니다.
   * "학교 전체의 전기 사용량(CPU 총 사용량)은 어떤가?"
   * "중앙 난방은 잘 되고 있는가? (CPU 온도)"
   * "물탱크에 물은 충분히 남아있는가? (메모리 총사용량)"
   * "창고 공간은 얼마나 비어있는가? (디스크 잔여 용량)"
   * "중앙 현관 출입은 원활한가? (네트워크 트래픽)"

  2. 왜 필요한가?

  cAdvisor는 컨테이너가 사용하는 리소스를, Metrics Server는 그 요약본을 알려줍니다. 하지만 이것만으로는 전체 서버의 상태를 알 수 없습니다. 서버 한 대에는 우리가 배포한 컨테이너만 실행되는 것이 아니라, 운영체제(OS) 자체, kubelet 등 다른 중요한 시스템 프로세스들도 함께 실행되기 때문입니다.

  node-exporter는 바로 이 "컨테이너 밖" 세상의 정보를 제공하여 모니터링의 빈틈을 메워줍니다.

   * "특정 노드의 디스크 공간이 꽉 차서 더 이상 파드를 생성하지 못하는 건 아닐까?"
   * "컨테이너는 CPU를 적게 쓰는데, OS 버그 때문에 노드 전체의 CPU 사용량이 100%인 건 아닐까?"
   * "네트워크 카드에 물리적인 문제가 생긴 건 아닐까?"
   * "서버의 메모리가 부족해서 시스템이 느려진 건 아닐까?"

  이런 근본적인 인프라 문제를 진단하려면 반드시 node-exporter가 제공하는 정보가 필요합니다.

  3. 어떻게 동작하는가?

   1. DaemonSet으로 배포: node-exporter는 보통 쿠버네티스에서 DaemonSet이라는 방식으로 배포됩니다. DaemonSet은 클러스터의 모든 노드에 이 파드를 하나씩 반드시 실행하도록 보장해 줍니다. 즉, 학교 건물마다 시설 관리인이 한 명씩 상주하는 것과 같습니다.
   2. OS 정보 수집: 각 노드에서 실행된 node-exporter 파드는 해당 노드의 운영체제 커널이 제공하는 정보 파일들(주로 /proc, /sys 디렉터리)을 읽어서 서버의 상태를 파악합니다.
   3. 메트릭 노출: 수집한 모든 정보를 Prometheus가 이해할 수 있는 텍스트 형식으로 변환하여 자신의 /metrics 엔드포인트(기본 포트 9100)에 노출합니다.

  [ 데이터 흐름 ]
  각 서버(Node)의 OS → node-exporter (DaemonSet) → (스크랩) → Prometheus

  4. 어떤 메트릭을 제공하는가? (예시)

  node-exporter는 수백 가지의 상세한 하드웨어/OS 메트릭을 제공합니다.

   * CPU 관련
       * node_cpu_seconds_total: CPU가 각 모드(user, system, idle 등)에서 소비한 시간
       * node_load1, node_load5, node_load15: 시스템의 1분, 5분, 15분 평균 부하

   * 메모리 관련
       * node_memory_MemTotal_bytes: 전체 물리 메모리 크기
       * node_memory_MemAvailable_bytes: 애플리케이션이 즉시 사용할 수 있는 가용 메모리 크기 (매우 중요!)

   * 디스크 관련
       * node_filesystem_size_bytes: 파일 시스템의 전체 크기
       * node_filesystem_avail_bytes: 사용 가능한 디스크 공간 크기
       * node_disk_read_bytes_total, node_disk_written_bytes_total: 디스크 읽기/쓰기 총량

   * 네트워크 관련
       * node_network_receive_bytes_total: 네트워크 인터페이스별 데이터 수신 총량
       * node_network_transmit_bytes_total: 네트워크 인터페이스별 데이터 송신 총량

  5. 최종 비교: 쿠버네티스 모니터링의 완성

  이제 네 가지 도구의 역할을 종합하여 비교할 수 있습니다.

|구분 | cAdvisor|Metrics Server|kube-state-metrics| node-exporter|
|------|------|------|------|------|
|주요 역할|컨테이너 리소스 상세 측정|리소스 사용량 요약 및 집계|쿠버네티스 오브젝트 상태 변환| 서버 머신(OS/하드웨어) 상태 측정|
|관점|컨테이너 내부|쿠버네티스 리소스|쿠버네티스 API|서버(노드) 자체|
|제공 정보 |CPU, 메모리 등|CPU, 메모리 |오브젝트 개수, 상태 등|CPU, 메모리, 디스크, 네트워크 등 시스템 전반|
| K8s 인지|O|O|O| X (모름)|
|주요 사용처|Prometheus|HPA, kubectl top|Prometheus| Prometheus|

  결론적으로, Prometheus가 `cAdvisor`, `kube-state-metrics`, `node-exporter` 세 가지를 모두 수집할 때 비로소 컨테이너부터 서버 하드웨어까지 아우르는 완전한 클러스터 모니터링 시스템이 구축됩니다.


node-exporter를 쿠버네티스 환경에 설치하고 사용하는 방법을 단계별로 알려드리겠습니다.

node-exporter의 핵심은 DaemonSet으로 배포하여 클러스터의 모든 노드에서 서버의 물리적인 메트릭을 수집하게 하는 것입니다.

  ---

  1단계: node-exporter 설치용 YAML 파일 생성

  node-exporter를 배포하기 위해 필요한 DaemonSet과 Service 리소스를 정의하는 YAML 파일을 생성하겠습니다.

  1.1. 권한 설정 (RBAC)
  node-exporter가 노드의 정보를 읽을 수 있도록 최소한의 권한을 부여합니다.

```
vi node-exporter-rbac.yaml

# --- ServiceAccount --- #
# ServiceAccount는 파드가 쿠버네티스 API 서버와 통신할 때 사용하는 '계정' 또는 '신원'을 제공합니다.
apiVersion: v1
kind: ServiceAccount
metadata:
  name: node-exporter # 'node-exporter'라는 이름의 서비스 계정을 생성합니다.
  namespace: kube-system # 관리의 용이성을 위해 kube-system 네임스페이스에 생성합니다.

---
# --- ClusterRole --- #
# ClusterRole은 클러스터 전역에 적용되는 권한들의 집합을 정의합니다.
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-exporter # 'node-exporter'라는 이름의 클러스터 역할을 정의합니다.
rules:
# 이 역할이 어떤 리소스에 대해 어떤 작업을 할 수 있는지 정의하는 규칙입니다.
# node-exporter의 일부 수집기가 노드, 서비스, 파드 정보를 필요로 할 수 있어 추가합니다.
- apiGroups: [""]
  resources:
  - nodes
  - services
  - pods
  verbs: ["list", "watch"] # 해당 리소스들을 '읽고(list)' '감시할(watch)' 수 있는 권한을 부여합니다.

---
# --- ClusterRoleBinding --- #
# ClusterRoleBinding은 특정 계정(ServiceAccount)에게 특정 역할(ClusterRole)을 '연결'해주는 역할을 합니다.
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: node-exporter
roleRef: # 연결할 역할을 지정합니다.
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: node-exporter # 위에서 정의한 'node-exporter' ClusterRole을 지정합니다.
subjects: # 이 권한을 부여받을 대상을 지정합니다.
- kind: ServiceAccount
  name: node-exporter # 위에서 생성한 'node-exporter' ServiceAccount를 지정합니다.
  namespace: kube-system

```

✦ 1.2. DaemonSet 및 Service
  DaemonSet은 모든 노드에 node-exporter 파드를 하나씩 배포하는 역할을 합니다. Service는 이렇게 배포된 파드들을 Prometheus가 쉽게 찾아 수집할 수 있도록 단일 엔드포인트를 제공합니다.

```
vi node-exporter-daemonset.yaml

# --- DaemonSet --- #
# DaemonSet은 클러스터의 모든 (또는 특정) 노드에 파드의 복제본이 하나씩 실행되도록 보장합니다.
# 노드 모니터링 에이전트를 배포할 때 가장 일반적으로 사용됩니다.
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: kube-system
  labels:
    app: node-exporter
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      # serviceAccountName: 이 파드가 사용할 서비스 계정의 이름입니다.
      serviceAccountName: node-exporter
      # hostNetwork: 파드가 호스트(노드)의 네트워크 네임스페이스를 직접 사용하도록 설정합니다.
      # 이를 통해 노드의 실제 네트워크 인터페이스 정보를 정확히 모니터링할 수 있습니다.
      hostNetwork: true
      # hostPID: 파드가 호스트(노드)의 프로세스 ID 네임스페이스를 공유하도록 합니다.
      hostPID: true
      containers:
      - name: node-exporter
        image: prom/node-exporter:latest
        ports:
        - containerPort: 9100
          protocol: TCP
          name: http
        # volumeMounts: 컨테이너 내부에 마운트할 볼륨을 정의합니다.
        volumeMounts:
        - name: proc
          mountPath: /host/proc # 호스트의 /proc 디렉터리를 컨테이너의 /host/proc에 마운트
          readOnly: true
        - name: sys
          mountPath: /host/sys # 호스트의 /sys 디렉터리를 컨테이너의 /host/sys에 마운트
          readOnly: true
        - name: root
          mountPath: /rootfs # 호스트의 루트(/) 디렉터리를 컨테이너의 /rootfs에 마운트
          readOnly: true
      # volumes: 파드가 사용할 볼륨을 정의합니다.
      # hostPath를 사용하여 호스트 노드의 파일시스템에 직접 접근합니다.
      # node-exporter가 노드의 OS 정보를 읽기 위해 필수적인 설정입니다.
      volumes:
      - name: proc
        hostPath:
          path: /proc
      - name: sys
        hostPath:
          path: /sys
      - name: root
        hostPath:
          path: /

---
# --- Service --- #
# Service는 여러 파드에 대한 안정적인 단일 접근점을 제공합니다.
apiVersion: v1
kind: Service
metadata:
  name: node-exporter
  namespace: kube-system
  labels:
    app: node-exporter
spec:
  selector:
    # app: node-exporter 레이블을 가진 모든 파드(즉, 모든 노드의 node-exporter)를 대상으로 합니다.
    app: node-exporter
  ports:
  - name: http
    port: 9100 # 9100번 포트로 서비스를 노출합니다.
    protocol: TCP

```

✦ 2단계: node-exporter 설치

  생성한 YAML 파일들을 클러스터에 적용합니다.

```
kubectl apply -f node-exporter-rbac.yaml
kubectl apply -f node-exporter-daemonset.yaml
```

  3단계: 설치 확인

  DaemonSet이 정상적으로 배포되었는지, 그리고 클러스터의 모든 노드에 node-exporter 파드가 하나씩 실행되고 있는지 확인합니다.
```
# -n kube-system 네임스페이스에서 확인합니다.
kubectl get daemonset -n kube-system node-exporter
```
  DESIRED, CURRENT, READY 등의 숫자가 모두 클러스터의 노드 수와 일치해야 합니다.

```
# 실행 중인 파드 목록을 확인합니다.
kubectl get pods -n kube-system -l app=node-exporter
```
  클러스터의 노드 개수만큼의 파드가 Running 상태로 보여야 합니다.

  4단계: 메트릭 데이터 접근 및 확인

  이제 특정 노드에 실행 중인 node-exporter에 직접 접근하여 메트릭을 확인해 보겠습니다.

  1. 특정 노드의 `node-exporter` 파드 이름 확인

  여러 파드 중 첫 번째 파드의 이름을 변수에 저장합니다.

```
export NE_POD_NAME=$(kubectl get pods -n kube-system -l app=node-exporter -o jsonpath=
     '{.items[0].metadata.name}')
```
  2. 포트 포워딩 실행

  내 컴퓨터의 9100 포트와 위에서 선택한 파드의 9100 포트를 연결합니다.

```
# -n kube-system 네임스페이스의 파드에 연결합니다.
kubectl port-forward -n kube-system $NE_POD_NAME 9100
```
  이 터미널은 계속 실행 상태로 두세요.

  3. 메트릭 확인 및 해석

  새 터미널을 열고 curl로 메트릭을 요청합니다. 이 데이터는 포트 포워딩으로 연결된 특정 노드 한 대의 상태 정보입니다.

```
curl http://localhost:9100/metrics
```
   * 예시 1: 노드의 사용 가능한 메모리 확인
```
curl -s http://localhost:9100/metrics | grep 'node_memory_MemAvailable_bytes'

#[결과]

HELP node_memory_MemAvailable_bytes Memory information field MemAvailable_bytes.
TYPE node_memory_MemAvailable_bytes gauge
```
