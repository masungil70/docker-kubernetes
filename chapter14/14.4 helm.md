### Helm: 쿠버네티스의 패키지 매니저

  Helm을 한마디로 정의하면 '쿠버네티스의 패키지 매니저(Package Manager)'입니다. 리눅스 환경에서 apt나 yum, macOS에서 brew, Node.js에서 npm을 사용하는 것과 동일한 역할을 쿠버네티스에서 수행합니다.

  Helm이 왜 필요한가요?

  쿠버네티스에 애플리케이션 하나를 배포하려면 보통 여러 개의 리소스가 필요합니다. 예를 들어, 웹 애플리케이션 하나를 배포하더라도 다음과 같은 다양한 YAML 파일을 작성해야 합니다.

   * Deployment: 애플리케이션 파드(Pod)를 관리
   * Service: 애플리케이션을 외부에 노출
   * ConfigMap: 설정 정보를 분리
   * Secret: 비밀번호나 API 키 등 민감한 정보를 관리
   * Ingress: 외부 요청을 서비스로 라우팅
   * PersistentVolumeClaim: 데이터 저장을 위한 볼륨 요청

  애플리케이션이 복잡해질수록 이 YAML 파일의 수는 기하급수적으로 늘어나고, 서로 간의 의존성도 복잡해져 수동으로 관리하기가 매우 어려워집니다. Helm은 바로 이 문제를 해결하기 위해 등장했습니다.

  Helm의 핵심 개념 3가지

  Helm을 이해하기 위해서는 다음 세 가지 핵심 개념을 알아야 합니다.

   1. 차트 (Chart)
       * Helm에서 사용하는 패키지 형식입니다.
       * 애플리케이션을 구성하는 데 필요한 모든 쿠버네티스 리소스 정의(YAML 템플릿), 의존성, 설정 값 등이 하나의 디렉토리 구조로 묶여 있습니다.
       * 주요 구성 요소:
           * templates/: 쿠버네티스 리소스 YAML 파일의 '틀'이 들어있는 디렉토리입니다. 변수를 사용하여 재사용 가능하게 만듭니다.
           * values.yaml: templates/ 디렉토리의 템플릿에 주입될 기본 설정 값들을 정의하는 파일입니다. 이 파일만 수정하면 애플리케이션의 설정을 쉽게 변경할 수 있습니다.
           * Chart.yaml: 차트의 이름, 버전, 설명 등 차트에 대한 메타데이터를 담고 있는 파일입니다.

   2. 릴리즈 (Release)
       * 차트를 쿠버네티스 클러스터에 설치한 인스턴스를 의미합니다.
       * 하나의 차트를 가지고 여러 환경(예: 개발용, 스테이징용, 운영용)에 각기 다른 설정으로 배포할 수 있는데, 이렇게 배포된 각각을 '릴리즈'라고 부릅니다.
       * 예를 들어, my-app이라는 차트를 dev-db와 prod-db라는 두 개의 다른 릴리즈 이름으로 설치할 수 있습니다.

   3. 리포지토리 (Repository)
       * 차트를 저장하고 공유하는 공간입니다.
       * apt나 yum의 리포지토리처럼, 공개된 차트나 조직 내부에서 사용하는 비공개 차트를 모아두고 필요할 때 가져와서 사용할 수 있습니다.
       * 대표적으로 Bitnami, Artifact Hub 등 여러 공개 리포지토리가 있습니다.

  Helm 사용의 장점

   * 복잡성 관리: 수많은 YAML 파일을 하나의 차트로 묶어 관리하므로 배포가 매우 단순해집니다.
   * 재사용성: 잘 만들어진 차트(예: PostgreSQL, Redis, Jenkins 등)를 가져와 간단한 설정 변경만으로 내 클러스터에 쉽게 설치할 수 있습니다.
   * 쉬운 설정: values.yaml 파일만 수정하거나 helm install 명령어에 옵션을 추가하여 애플리케이션의 설정을 손쉽게 변경할 수 있습니다.
   * 신뢰성 있는 릴리즈 관리: 다음과 같은 명령어로 애플리케이션의 전체 생명주기를 관리할 수 있습니다.
       * helm install: 새로운 릴리즈 설치
       * helm upgrade: 기존 릴리즈를 새로운 버전의 차트나 설정으로 업그레이드
       * helm rollback: 업그레이드에 문제가 생겼을 때 이전 버전으로 쉽게 되돌리기
       * helm uninstall: 해당 릴리즈와 관련된 모든 쿠버네티스 리소스를 한 번에 삭제

###  Helm 클라이언트 설치 절차

  1단계: Helm 클라이언트 설치

   * Linux (스크립트 사용):
```
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
```

  2. 설치 확인:
  설치가 완료되면 다음 명령어로 버전을 확인하여 정상적으로 설치되었는지 검증합니다.
```
helm version
```
  예상 결과 
```  
  version.BuildInfo{Version:"v3.x.x", ...} 와 같은 결과가 출력되면 성공입니다.
```
  ---

  2단계: 차트 리포지토리 추가 및 검색

  설치할 애플리케이션 차트를 가져올 소스, 즉 리포지토리를 등록하고 원하는 차트를 검색합니다.

  1. 리포지토리 추가:
  Helm 차트들이 모여있는 저장소를 추가합니다. 가장 널리 쓰이는 bitnami 리포지토리를 예시로 추가해 보겠습니다.
```
# 'bitnami'라는 이름으로 공식 Bitnami 차트 리포지토리 URL을 추가합니다.
helm repo add bitnami https://charts.bitnami.com/bitnami
```

  2. 리포지토리 목록 업데이트:
  추가된 리포지토리에서 최신 차트 정보를 가져옵니다.
```
helm repo update
```

  3. 차트 검색:
  설치하고 싶은 애플리케이션을 검색합니다. 예를 들어 mysql을 검색해 보겠습니다.
```
helm search repo mysql
```
  이 명령은 bitnami/mysql, community/mysql 등 검색어와 일치하는 여러 차트 목록을 보여줍니다.

  ---

  3단계: 차트 설정 커스터마이징

  차트를 그대로 설치하는 경우는 거의 없습니다. 대부분의 경우, 내 환경에 맞게 설정을 변경해야 합니다.

  1. 설정 가능한 값 확인:
  차트에서 어떤 값들을 변경할 수 있는지 values.yaml 파일의 내용을 확인합니다.
```
# bitnami/mysql 차트가 제공하는 모든 설정 옵션을 화면에 출력합니다.
helm show values bitnami/mysql
```
  출력된 내용을 보고 데이터베이스 비밀번호, 서비스 타입, 리소스 제한 등 어떤 값을 변경할지 결정합니다.

  2. 설정 파일 생성 및 수정 (권장 방법):
  위에서 확인한 기본 values.yaml을 파일로 저장한 뒤, 직접 수정하여 설치에 사용합니다. 이 방법은 설정 내역을 파일로 관리할 수 있어 매우 유용합니다.

폴더 구조 
```
/step1
├── my-mysql-values.yaml       # 8.4.5 버전 
├── my-mysql-values9.3.yaml    # 9.3.0 버전 
└── my-mysql-values9.4.yaml    # 9.4.0 버전 
```

```
# 기본 values.yaml 파일을 my-mysql-values.yaml 이라는 이름으로 저장합니다.
helm show values bitnami/mysql > my-mysql-values.yaml

# 이제 vi my-mysql-values.yaml 파일을 에디터로 열어 원하는 값을 수정합니다.
# 예: 이미지 버전 변경, root 비밀번호 변경, 서비스 타입을 LoadBalancer로 변경 등
#
image:
  tag: 8.4.5-debian-12-r0              <-- 이 부분을 수정
 ... 
 auth:
   rootPassword: "my-secret-password"  <-- 이 부분을 수정
 ...
 service:
   type: LoadBalancer                 <-- 이 부분을 수정
```

  3. `--set` 옵션 사용 (간단한 변경 시):
  파일을 만들기 번거롭고 몇 가지 간단한 값만 변경하고 싶을 때는 --set 옵션을 사용할 수 있습니다.
```
--set image.tag=8.4.5-debian-12-r0, auth.rootPassword=my-secret-password,service.type=ClusterIP
```
  ---

  4단계: 차트 설치 (릴리즈 생성)

  이제 커스터마이징한 설정을 사용하여 클러스터에 차트를 설치합니다. 설치된 인스턴스를 릴리즈(Release)라고 부릅니다.
```
# helm install <릴리즈_이름> <차트_이름> -f <설정_파일>
helm install my-production-mysql bitnami/mysql -f my-mysql-values.yaml
```
   * my-production-mysql: 내가 생성한 릴리즈의 고유한 이름입니다. 나중에 이 이름으로 릴리즈를 관리합니다.
   * bitnami/mysql: 설치할 차트의 이름입니다 (<리포지토리_이름>/<차트_이름>).
   * -f my-mysql-values.yaml: 3단계에서 수정한 설정 파일을 사용하겠다는 의미입니다.

  설치가 시작되면 Helm은 my-mysql-values.yaml의 값들을 차트 템플릿에 적용하여 최종 쿠버네티스 YAML을 생성하고, 이를 클러스터 API 서버에 전달하여 리소스들을 생성합니다.


 helm install 명령어의 실행 결과를 항목별로 자세히 설명해 드리겠습니다. Helm이 성공적으로 차트를 배포한 후, 사용자에게 유용한 정보를 제공하는 요약본입니다.

  ---

  1. 릴리즈 기본 정보

```
   NAME: my-production-mysql
   LAST DEPLOYED: Sat Sep  6 00:07:01 2025
   NAMESPACE: default
   STATUS: deployed
   REVISION: 1
```
   * NAME: 당신이 설치한 릴리즈의 고유한 이름입니다. 앞으로 helm status, helm upgrade, helm uninstall 등 이 릴리즈를 관리할 때 이 이름을 사용합니다.
   * LAST DEPLOYED: 이 릴리즈가 마지막으로 배포된 시간입니다.
   * NAMESPACE: 이 릴리즈가 설치된 쿠버네티스 네임스페이스입니다. 별도로 지정하지 않았기 때문에 default 네임스페이스에 설치되었습니다.
   * STATUS: 릴리즈의 현재 상태입니다. deployed는 성공적으로 배포되었음을 의미합니다. 만약 실패했다면 failed 등으로 표시됩니다.
   * REVISION: 릴리즈의 버전 번호입니다. 처음 설치했기 때문에 1입니다. 나중에 helm upgrade를 실행하면 이 번호가 2, 3으로 올라갑니다.

  ---

  2. 차트 및 앱 버전 정보
```
   CHART NAME: mysql
   CHART VERSION: 14.0.3
   APP VERSION: 9.4.0
```
   * CHART NAME: 설치된 Helm 차트의 이름입니다.
   * CHART VERSION: 설치된 mysql 차트의 버전입니다. 차트 자체도 버그 수정이나 기능 추가로 계속 업데이트됩니다.
   * APP VERSION: 이 차트가 배포하는 실제 애플리케이션, 즉 MySQL의 버전입니다.

  3. Bitnami 정책 경고
```
   ⚠ WARNING: Since August 28th, 2025, only a limited subset of images/charts are available for free.
   Subscribe to Bitnami Secure Images to receive continued support and security updates.
```
   * 차트 제공자인 Bitnami의 정책 변경에 대한 안내입니다. 특정 날짜 이후로 일부 이미지/차트는 무료 사용이 제한되며, 지속적인 지원과 보안 업데이트를 받으려면 유료 구독이 필요할 수 있다는 내용입니다. 학습 및 테스트 목적에는 큰 문제가 없지만, 상용 환경에서는 확인이 필요합니다.

  4. 배포 확인 팁 및 연결 방법 (가장 중요한 부분)

  이 부분은 차트 개발자가 사용자를 위해 남겨놓은 친절한 안내서(NOTES)입니다.
```
** Please be patient while the chart is being deployed **

Tip:

  Watch the deployment status using the command: kubectl get pods -w --namespace default
```
   * 배포 팁: kubectl get pods -w 명령을 사용하면 MySQL 파드가 생성되고 실행되는 과정을 실시간으로 모니터링할 수 있다는 안내입니다. Pending -> ContainerCreating -> Running 상태로 변하는 것을 볼 수 있습니다.
```
Services:

echo Primary: my-production-mysql.default.svc.cluster.local:3306
```
   * 서비스 주소: 쿠버네티스 클러스터 내부에서 데이터베이스에 접근할 때 사용하는 DNS 주소입니다. 클러스터 안의 다른 애플리케이션이 이 주소를 통해 MySQL에 연결할 수 있습니다.
```
Execute the following to get the administrator credentials:

   echo Username: root
   MYSQL_ROOT_PASSWORD=$(kubectl get secret --namespace default my-production-mysql -o jsonpath="{.data.mysql-root-password}" | base64 -d)

```
   * 관리자(root) 비밀번호 확인 방법:
       1. Helm은 보안을 위해 MySQL root 계정의 비밀번호를 무작위로 생성하여 쿠버네티스의 Secret이라는 보안 저장소에 저장합니다.
       2. 위 kubectl get secret ... 명령어는 my-production-mysql이라는 Secret에서 mysql-root-password 값을 추출한 뒤, Base64로 인코딩된 값을 디코딩(base64 -d)하여 MYSQL_ROOT_PASSWORD라는 셸 변수에 저장하는 명령어입니다. 이 명령을 터미널에 그대로 복사/붙여넣기하여 실행하면 비밀번호를 얻을 수 있습니다.
```
 To connect to your database:

   1. Run a pod that you can use as a client:
       kubectl run my-production-mysql-client ...

   2. To connect to primary service (read/write):
       mysql -h my-production-mysql.default.svc.cluster.local -uroot -p"$MYSQL_ROOT_PASSWORD"
```
   * 데이터베이스 연결 절차:
       1. MySQL 서비스는 기본적으로 클러스터 내부에서만 접근 가능하므로, 외부에서 바로 접속할 수 없습니다. 따라서 접속 테스트를 위해 클러스터 내부에 임시 클라이언트 파드를 하나 실행하라는 안내입니다. kubectl run ... 명령이 그 역할을 합니다.
       2. 1번에서 생성한 클라이언트 파드 안에서, mysql -h ... 명령을 실행하여 데이터베이스에 접속하라는 의미입니다. 위에서 얻은 비밀번호 변수($MYSQL_ROOT_PASSWORD)를 그대로 사용합니다.

  5. 추가 경고 (리소스 설정)
```
WARNING: There are "resources" sections in the chart not set. ... For production installations, please set the following values according to your workload needs:
   - primary.resources
   - secondary.resources
```
   * 리소스 미설정 경고: my-mysql-values.yaml 파일에 이 MySQL 파드가 사용할 CPU와 메모리의 양(resources)을 지정하지 않았다는 경고입니다.
   * 의미: 리소스 제한을 설정하지 않으면 MySQL이 서버의 모든 자원을 다 사용해버려 다른 애플리케이션에 영향을 줄 수 있습니다. 테스트 환경에서는 괜찮지만, 운영(Production) 환경에서는 반드시 `primary.resources`와 `secondary.resources` 항목을 설정하여 안정성을 확보해야 합니다.

  1. NFS 프로비저너 Helm 리포지토리 추가 및 업데이트
```
helm repo add nfs-subdir-external-provisioner https://kubernetes-sigs.github.io/nfs-subdir-external-provisioner/
helm repo update
```

   2. NFS 프로비저너 설치
       * 이 명령은 nfs-provisioner라는 이름의 릴리즈를 생성합니다.
       * nfs.server에는 알려주실 IP 주소를, nfs.path에는 /mnt/nfs/db_data를 설정합니다.
       * storageClass.defaultClass=true 옵션을 통해, 새로 생성될 nfs-storage라는 이름의 스토리지 클래스를 클러스터의 기본값으로 지정합니다. 이렇게 하면 MySQL 차트가 별도 수정 없이 이 스토리지를 사용하게 됩니다.

```
helm install nfs-provisioner nfs-subdir-external-provisioner/nfs-subdir-external-provisioner \
 --set nfs.server=192.168.80.165 \
 --set nfs.path=/mnt/nfs/db_data \
 --set storageClass.name=nfs-storage \
 --set storageClass.defaultClass=true
```

설치가 완료되면 DB 서버의 버전을 확인할 수 있습니다 
```
kubectl exec my-production-mysql-0 -- mysql --version

```
예상 실행 결과 
Defaulted container "mysql" out of: mysql, preserve-logs-symlinks (init)
mysql  Ver 8.4.5 for Linux on x86_64 (Source distribution)


  5단계: 릴리즈 관리

  설치가 끝이 아닙니다. 운영 중에는 릴리즈의 상태를 확인하고, 업그레이드하거나 삭제하는 등의 관리가 필요합니다.

  1. 릴리즈 목록 확인:
  현재 클러스터에 설치된 모든 릴리즈를 확인합니다.
```
helm list
# 또는 축약형으로 helm ls
```

  2. 릴리즈 상태 확인:
  특정 릴리즈의 상세 상태와 배포된 리소스들을 확인합니다.
```
helm status my-production-mysql
```

  3. 릴리즈 업그레이드:
  애플리케이션 버전을 올리거나 설정을 변경하고 싶을 때 사용합니다.
```
# my-new-values.yaml 파일을 새로 수정했다고 가정
helm upgrade my-production-mysql bitnami/mysql -f my-mysql-values9.3.yaml
```
  설치가 완료되면 DB 서버의 버전을 확인할 수 있습니다 
```
kubectl exec my-production-mysql-0 -- mysql --version
```
  예상 실행 결과 

  Defaulted container "mysql" out of: mysql, preserve-logs-symlinks (init)
  mysql  Ver 9.3.0 for Linux on x86_64 (Source distribution)


  4. 릴리즈 롤백:
  업그레이드 후 문제가 발생했을 때 이전 버전으로 되돌립니다.
```
# 먼저 릴리즈의 히스토리를 확인하여 롤백할 리비전(REVISION) 번호를 찾습니다.
helm history my-production-mysql

# 1번 리비전으로 롤백합니다.
helm rollback my-production-mysql 1

리비전으로 롤백이 완료되면 DB 서버의 버전을 확인할 수 있습니다 
kubectl exec my-production-mysql-0 -- mysql --version

```

  5. 릴리즈 삭제:
  설치된 릴리즈와 관련된 모든 쿠버네티스 리소스(Deployment, Service, PVC 등)를 한 번에 삭제합니다.
```
helm uninstall my-production-mysql
```

  이것이 Helm을 사용하여 애플리케이션을 배포하고 관리하는 표준적인 절차입니다. 이 과정을 통해 복잡한 쿠버네티스 애플리케이션을 체계적이고 반복 가능하게 관리할 수 있습니다.

###  예제 : heml을 사용하여 nginx을 설치 관리하는 방법


  Nginx 설치 및 관리 절차

  1단계: Helm 리포지토리 추가 및 업데이트

  Nginx 차트를 제공하는 리포지토리를 추가하고 최신 정보를 가져옵니다. 여기서는 가장 널리 사용되는 bitnami 리포지토리를 사용하겠습니다.
```
# bitnami 리포지토리 추가
helm repo add bitnami https://charts.bitnami.com/bitnami

# 리포지토리 최신 정보 업데이트
helm repo update
```

폴더 구조 
```
step2
├── manage-nginx.sh      #heml 관리용 스크립트 
└── nginx-values.yaml    #nginx values 파일
```

  1. Nginx 설정 파일: nginx-values.yaml

  파일 생성 이유:
  이 파일은 Helm으로 Nginx를 설치할 때, 기본 설정값을 덮어쓰고 우리가 원하는 설정으로 변경하기 위해 필요합니다. 예를 들어, 외부에서 Nginx에 접속하는 방식(Service Type), Nginx 서버의 개수(Replica Count) 등을 이 파일에 정의할 수 있습니다. 설정을 코드로 관리(Configuration as Code)하게 되어, 언제든지 동일한 설정으로 Nginx를 다시 배포할 수 있습니다.

  파일의 역할:
  helm install 명령어 실행 시 -f 옵션으로 이 파일을 지정하면, Helm은 Nginx 차트의 기본 values.yaml과 이 파일의 내용을 병합합니다. 여기서 지정한 값이 기본값을 덮어쓰게 되어, 최종적으로 우리가 원하는 설정의 쿠버네티스 리소스(Deployment, Service 등)가 생성됩니다.

  이제 step2/nginx-values.yaml 파일을 아래와 같이 생성합니다.
```
# ==============================================================================
# ## Nginx Helm Chart 사용자 정의 설정 (nginx-values.yaml) ##
# ==============================================================================
# 이 파일은 Bitnami Nginx 차트의 기본값을 덮어쓰기 위한 설정 파일입니다.
# 주석 처리되지 않은 값들이 기본값을 변경하여 적용됩니다.

# ## 복제본 수 (Replica Count) ##
# 실행할 Nginx 파드(Pod)의 개수를 지정합니다.
# 기본값은 1이지만, 트래픽 분산을 위해 2개 이상으로 설정할 수 있습니다.
replicaCount: 2

# ## 서비스 (Service) 설정 ##
# Nginx를 쿠버네티스 클러스터 내/외부에 노출하는 방식을 정의합니다.
service:
  # ## 서비스 타입 (Service Type) ##
  # - ClusterIP: 클러스터 내부에서만 접근 가능 (기본값)
  # - NodePort: 각 노드(서버)의 특정 포트를 통해 외부에서 접근 가능
  # - LoadBalancer: 클라우드 공급자(AWS, GCP 등)의 로드밸런서를 통해 외부 IP를 할당받아 접근
  # 여기서는 외부 테스트를 용이하게 하기 위해 'NodePort'로 변경합니다.
  type: NodePort
  # NodePort로 설정했을 때, 각 노드에 할당될 포트 번호를 지정할 수 있습니다.
  # 지정하지 않으면 30000-32767 사이의 임의의 포트가 할당됩니다.
  # nodePorts:
  #   http: 30080
  #   https: 30443

# ## 리소스 제한 (Resource Limits) ##
# 각 Nginx 파드가 사용할 수 있는 CPU와 메모리의 최대 양을 지정합니다.
# 안정적인 운영을 위해 설정하는 것을 권장합니다.
# resources:
#   limits:
#     cpu: 100m
#     memory: 128Mi
#   requests:
#     cpu: 100m
#     memory: 128Mi

# ## Ingress 설정 ##
# Ingress 컨트롤러를 사용하여 도메인 기반으로 Nginx에 접근하게 할 때 설정합니다.
# 여기서는 사용하지 않으므로 비활성화(enabled: false) 상태로 둡니다.
ingress:
  enabled: false
```
  ---

  2. Nginx 설치 및 관리 절차 스크립트: manage-nginx.sh

```
vi manage-nginx.sh

# 네임스페이스 없이 기본 네임스페이스에 설치하려면 아래 명령을 사용합니다.
helm install nginx-release bitnami/nginx -f nginx-values.yaml

# 또는 아래 명령으로도 서비스 클러스터IP 정보를 확인할 수 있습니다.
kubectl get svc

```

실행하기 위해 실행 권한을 설정해주세요 
```
chmod +x manage-nginx.sh
```
