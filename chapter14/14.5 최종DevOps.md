###  쿠버네티스 환경에서 Helm을 사용해 프로메테우스를 설치하는 절차

  여기서는 가장 널리 사용되는 kube-prometheus-stack 차트를 기준으로 설명합니다. 이 차트는 프로메테우스뿐만 아니라 그라파나(Grafana), 얼럿매니저(Alertmanager), 각종 익스포터(Exporter) 등 모니터링에 필요한 거의 모든 구성요소를 한 번에 설치해주는 합니다.

  ---

  Helm을 이용한 프로메테우스 설치 절차

  1단계: Helm 리포지토리 추가 및 업데이트

  프로메테우스 관련 차트가 포함된 공식 커뮤니티 리포지토리를 Helm에 추가해야 합니다.
```
# 1. 프로메테우스 커뮤니티 리포지토리 추가
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts

# 2. 최신 차트 정보를 가져오기 위해 리포지토리 업데이트
helm repo update
```
  이 명령어를 실행하면 prometheus-community라는 이름으로 원격 차트 저장소가 로컬 Helm 클라이언트에 등록됩니다.

  2단계: 설정(Values) 파일 준비 및 수정

  Helm의 가장 큰 장점은 values.yaml 파일을 통해 설치 설정을 손쉽게 변경할 수 있다는 점입니다. kube-prometheus-stack은 설정할 수 있는 항목이 매우 많기 때문에, 기본 설정 파일을 먼저 추출한 뒤 필요한 부분만 수정하여 사용하는 것이 좋습니다.
```
# 기본 values.yaml 파일을 로컬에 저장
helm show values prometheus-community/kube-prometheus-stack > custom-values.initial.yaml
```
  이제 custom-values.yaml 파일을 열어 원하는 설정을 수정합니다. 처음 설치 시 주로 변경하는 핵심 설정은 다음과 같습니다.

  주요 설정 항목 (in `custom-values.initial.yaml`):

   1. Grafana 설정 (비밀번호 및 서비스 타입)
       * 관리자 비밀번호 설정: grafana.adminPassword 항목의 주석을 풀고 원하는 비밀번호를 입력합니다. (설정하지 않으면 설치 시 임의의 비밀번호가 생성됩니다.)
       * 외부 접속 방식 변경: grafana.service.type을 ClusterIP (기본값, 클러스터 내부에서만 접속)에서 LoadBalancer 또는 NodePort로 변경하면 외부에서 Grafana 대시보드에 쉽게 접속할 수 있습니다.
```
# custom-values.initial.yaml 예시
# 이 파일은 kube-prometheus-stack의 초기 설치를 위한 values.yaml 샘플입니다.
# 설치 전에 반드시 내용을 검토하고 필요한 부분을 수정하세요.

alertmanager:
  enabled: true # Alertmanager 활성화 (기본값)
  # Alertmanager 서비스 타입 설정 (NodePort 또는 LoadBalancer로 변경 가능)
  service:
    type: ClusterIP

grafana:
  enabled: true # Grafana 활성화 (기본값)
  # Grafana 관리자 비밀번호 설정 (설정하지 않으면 임의의 비밀번호가 생성됩니다)
  adminPassword: "1004" # <-- 여기에 원하는 비밀번호 입력
  # Grafana 서비스 타입 설정 (NodePort 또는 LoadBalancer로 변경 가능)
  service:
    type: NodePort

# Node Exporter 활성화 (기본값)
nodeExporter:
  enabled: true

# Kube State Metrics 활성화 (기본값)
kubeStateMetrics:
  enabled: true

```
   2. Prometheus 데이터 영구 저장 (Persistence)
       * 기본적으로 프로메테우스 Pod이 재시작되면 수집했던 모든 메트릭 데이터가 사라집니다. 데이터를 영구적으로 보존하려면 PersistentVolume을 사용하도록 설정해야 합니다.
       * prometheus.prometheusSpec.storageSpec 항목을 찾아 주석을 해제하거나 추가합니다. (사전에 PersistentVolumeClaim을 생성할 수 있는 StorageClass가 클러스터에 설정되어 있어야 합니다.)
```
# custom-values.initial.yaml 예시
...
prometheus:
  prometheusSpec:
    # 프로메테우스 데이터 영구 저장을 위한 설정
    storageSpec:
      volumeClaimTemplate:
        spec:
          # 요청하신 'nfs' 스토리지 클래스를 사용하도록 설정
          storageClassName: nfs # <-- 자신의 NFS StorageClass 이름으로 변경
          accessModes: ["ReadWriteOnce"]
          resources:
            requests:
              # 프로메테우스 데이터 저장 공간 크기 (필요에 따라 조절)
              storage: 20Gi
...
```

   3. Alertmanager 설정
       * alertmanager.enabled: true (기본값)인지 확인합니다.
       * Grafana와 마찬가지로 alertmanager.service.type을 변경하여 외부에서 접근할 수 있습니다.

  이 외에도 Ingress 설정, 각 컴포넌트의 리소스 할당량(CPU, Memory) 등 매우 다양한 항목을 이 파일에서 제어할 수 있습니다.

  3단계: Helm 차트 설치

  이제 준비된 custom-values.yaml 파일을 사용하여 프로메테우스를 설치합니다. 모니터링 시스템은 별도의 네임스페이스에 설치하는 것이 일반적입니다. 여기서는 monitoring 네임스페이스를 사용하겠습니다.
```
# helm install [릴리즈 이름] [차트 이름] -n [네임스페이스] --create-namespace -f [설정 파일]

helm install prometheus prometheus-community/kube-prometheus-stack \
  -n monitoring \
  --create-namespace \
  -f custom-values.yaml
```
   * prometheus: 이번 설치에 부여하는 이름(릴리즈 이름)입니다. 나중에 업그레이드나 삭제 시 사용됩니다.
   * prometheus-community/kube-prometheus-stack: 설치할 차트의 이름입니다.
   * -n monitoring: monitoring 네임스페이스에 설치합니다.
   * --create-namespace: monitoring 네임스페이스가 없으면 자동으로 생성합니다.
   * -f custom-values.yaml: 2단계에서 수정한 설정 파일을 사용하겠다는 의미입니다.

  4단계: 설치 확인

  설치가 완료되면 monitoring 네임스페이스의 Pod들이 정상적으로 실행되는지 확인합니다.
```
kubectl get pods -n monitoring
```
  prometheus-operator, prometheus-k8s-0, grafana, alertmanager 등 여러 Pod들이 Running 상태로 표시되면 성공적으로 설치된 것입니다.

  5단계: 서비스 접속 (UI 확인)

  설치된 서비스(Grafana, Prometheus, Alertmanager)에 접속하여 UI를 확인합니다. kubectl get svc 명령어로 서비스 타입을 확인하고 접속 정보를 얻을 수 있습니다.
```
kubectl get svc -n monitoring
```
  만약 서비스 타입을 LoadBalancer로 설정했다면 EXTERNAL-IP 주소가 할당되며, 이 주소를 통해 접속할 수 있습니다. NodePort로 설정했다면 (클러스터 노드 IP):(포트 번호)로 접속합니다.


  요약

  그라파나는 프로메테우스를 포함한 다양한 곳에 흩어져 있는 복잡한 데이터를 가져와, 누구나 쉽게 이해할 수 있는 의미 있는 정보와 인사이트로 바꿔주는 강력한 시각화 도구입니다. 현대적인 모니터링 및 관측 가능성(Observability) 시스템에서 없어서는 안 될 핵심적인 구성 요소입니다.

  helm install 명령어로 prometheus-community/kube-prometheus-stack 차트를 설치하면, 프로메테우스와 그라파나가 자동으로 함께 설치됩니다.

  이름에 포함된 "스택(Stack)" 이라는 단어가 바로 그 의미입니다. 이 Helm 차트는 단순히 프로메테우스만 설치하는 것이 아니라, 현대적인 모니터링 환경(Observability Stack)을 구축하는 데 필요한 여러 핵심 컴포넌트들을 하나의 묶음으로 제공합니다.

  kube-prometheus-stack을 설치했을 때 기본적으로 함께 설치되는 주요 컴포넌트들은 다음과 같습니다.

   * ✅ Prometheus: 메트릭을 수집, 저장하는 핵심 서버
   * ✅ Grafana: 수집된 데이터를 시각화하는 대시보드 (미리 프로메테우스용 데이터 소스 설정 및 몇 가지 기본 대시보드가 포함되어 설치됩니다.)
   * ✅ Alertmanager: 프로메테우스에서 발생한 알림을 관리하고 라우팅하는 도구
   * ✅ Node Exporter: 쿠버네티스 클러스터의 각 노드(서버)의 CPU, 메모리, 디스크 등 시스템 메트릭을 수집하는 에이전트
   * ✅ Kube State Metrics: 디플로이먼트, 파드, 서비스 등 쿠버네티스 오브젝트의 상태 정보를 메트릭으로 변환해주는 컴포넌트
   * Prometheus Operator: 위의 모든 컴포넌트들을 쿠버네티스 환경에서 더 쉽게 배포하고 관리할 수 있도록 돕는 컨트롤러

  따라서, 앞선 가이드의 3단계(helm install ...)를 실행하면 별도의 추가 작업 없이도 즉시 프로메테우스로 데이터를 수집하고 그라파나로 그 데이터를 조회할 수 있는 완전한 환경이 구축됩니다.

### 최종 예제 
 FastAPI 애플리케이션 개발부터 쿠버네티스 배포, 성능 테스트, 모니터링, 오토스케일링, 알림 설정, 그리고 클러스터 노드 관리에 이르기까지 전체적인 DevOps 파이프라인을 구축하는 매우 포괄적인 과정입니다.

  개요

   1. FastAPI 애플리케이션 개발 및 계측(Instrumentation)
   2. 애플리케이션 컨테이너화 (Dockerfile)
   3. 쿠버네티스 배포 (Deployment, Service, Ingress)

  ---

  1단계: FastAPI 애플리케이션 개발 및 계측

  먼저, 사칙연산 API를 가진 FastAPI 앱을 만들고, 프로메테우스가 메트릭을 수집할 수 있도록 계측(Instrumentation) 코드를 추가합니다.
   1. 프로젝트 폴더 생성 및 파일 준비
```
mkdir 1_fastapi_app
cd 1_fastapi_app

```
   2. 필요한 라이브러리 설치
      starlette-prometheus는 FastAPI 앱의 요청 수, 응답 시간 등의 메트릭을 /metrics 엔드포인트에 자동으로 노출시켜주는 라이브러리입니다.

```    
vi requirements.txt 
fastapi
uvicorn
starlette-prometheus
```
   3. FastAPI 애플리케이션 코드 작성
```
vi main.py
from fastapi import FastAPI
from starlette.middleware.cors import CORSMiddleware
import uvicorn
# 프로메테우스 미들웨어 및 메트릭 엔드포인트 추가
from starlette_prometheus import metrics, PrometheusMiddleware

app = FastAPI()

# 프로메테우스 미들웨어 추가
app.add_middleware(PrometheusMiddleware)
# /metrics 엔드포인트를 앱에 추가
app.add_route("/metrics", metrics)

# 기본 경로
@app.get("/")
def read_root():
    return {"message": "Calculator API is running"}

# 덧셈
@app.get("/add")
def add(a: float, b: float):
    return {"result": a + b}

# 뺄셈
@app.get("/subtract")
def subtract(a: float, b: float):
    return {"result": a - b}

# 곱셈
@app.get("/multiply")
def multiply(a: float, b: float):
    return {"result": a * b}

# 나눗셈
@app.get("/divide")
def divide(a: float, b: float):
    if b == 0:
        return {"error": "Division by zero is not allowed"}
    return {"result": a / b}

@app.get("/calculate")
def calculate(iterations: int = 20000, inner_iterations: int = 1000):
    """
    의도적으로 CPU 부하를 80% 이상으로 높이기 위해 복잡한 연산을 수행합니다.
    (iterations * inner_iterations) 만큼의 연산이 수행됩니다.
    """
    result = 0
    # 0으로 나누거나 로그를 취하는 것을 피하기 위해 1부터 시작합니다.
    for i in range(1, iterations + 1):
        for j in range(1, inner_iterations + 1):
            # 좀 더 복잡하고 무거운 연산 수행
            result += math.log(i) * math.sin(j) - math.sqrt(j) * math.cos(i)
    
    return {"message": f"Heavy calculation finished after {iterations}x{inner_iterations} iterations."}


if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8000)

```

  2단계: 애플리케이션 컨테이너화 (Dockerfile)

  이제 이 FastAPI 앱을 실행할 수 있는 도커 이미지를 만듭니다.
```
vi Dockerfile 
# 1. 베이스 이미지 선택
FROM python:3.9-slim

# 2. 작업 디렉토리 설정
WORKDIR /app

# 3. 의존성 파일 복사 및 설치
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 4. 소스 코드 복사
COPY main.py .

# 5. 애플리케이션 실행
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

  이후, 도커 이미지를 빌드하여 Docker Hub 같은 이미지 레지스트리에 푸시합니다. (예: masungil/fastapi-calculator:v1)
```
# 이미지 빌드
docker build -t masungil/fastapi-calculator:v1 .


# 레지스트리에 푸시
docker push masungil/fastapi-calculator:v1
```
  3단계: 쿠버네티스 배포 (Deployment, Service, Ingress)

  Nginx Ingress Controller가 설치되어 있지 않다면, Helm을 사용하여 설치하겠습니다
  Nginx Ingress Controller는 공식 Helm 차트를 통해 쉽게 배포할 수 있습니다.

  Nginx Ingress Controller 설치 방법 (Helm 사용)

  1단계: Nginx Ingress Controller Helm 리포지토리 추가
```
# 1. Nginx Ingress Controller Helm 리포지토리 추가
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx

# 2. Helm 리포지토리 업데이트 (최신 차트 정보 가져오기)
helm repo update
```

  2단계: Nginx Ingress Controller 설치

  helm install 명령어를 사용하여 Nginx Ingress Controller를 배포합니다. 이때, 서비스 타입을 지정하여 외부에서 접근 가능하도록 설정할 수 있습니다. 온프레미스 환경에서는 NodePort 또는 LoadBalancer (MetalLB와 같은 소프트웨어 로드밸런서가 있는 경우)를 주로 사용합니다.

 LoadBalancer 타입으로 설치하는 예시

```
# Nginx Ingress Controller를 ingress-nginx 네임스페이스에 설치
helm install nginx-ingress ingress-nginx/ingress-nginx \
   3   --namespace ingress-nginx --create-namespace \
   4   --set controller.service.type=LoadBalancer \
   5   --set controller.service.externalTrafficPolicy=Local # 클라이언트 IP 보존
```
  `--set` 옵션 설명:

   * --namespace ingress-nginx --create-namespace: ingress-nginx라는 새로운 네임스페이스를 생성하고 그곳에 설치합니다.
   * --set controller.service.type=LoadBalancer: Ingress Controller의 서비스를 LoadBalancer 타입으로 생성합니다.
     (온프레미스에서 LoadBalancer가 작동하지 않으면 NodePort로 변경하세요.)
   * --set controller.service.externalTrafficPolicy=Local: 클라이언트의 실제 IP 주소를 보존합니다.

  `NodePort` 타입으로 설치하는 예시

  --set controller.service.type=LoadBalancer 부분을 --set controller.service.type=NodePort 로 변경하여 실행합니다.
```
# NodePort 타입으로 설치하는 예시
helm install nginx-ingress ingress-nginx/ingress-nginx \
  --namespace ingress-nginx --create-namespace \
  --set controller.service.type=NodePort \
  --set controller.service.externalTrafficPolicy=Local
```
  3단계: 설치 확인

  설치 명령을 실행한 후, Nginx Ingress Controller 파드와 서비스가 정상적으로 실행되는지 확인합니다.
```
# 파드 확인
kubectl get pods -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx

# 서비스 확인
kubectl get svc -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx
```

  LoadBalancer 타입으로 설치했다면 EXTERNAL-IP가 할당될 때까지 시간이 걸릴 수 있습니다. NodePort 타입이라면 서비스의 PORT(S) 컬럼에서 NodePort를 확인할 수 있습니다.

  Nginx Ingress Controller가 성공적으로 배포되면, 이제 calculator-app.yaml에 정의된 Ingress 리소스(calculator-ingress)가 작동하여 calculator.example.com 도메인을 통해 FastAPI 애플리케이션에 접근할 수 있게 됩니다.

  이제 쿠버네티스 클러스터에 FastAPI 앱을 배포합니다. 하나의 파일에 Deployment, Service, Ingress를 모두 정의하겠습니다.


```
vi calculator-app.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: calculator-deployment
spec:
  replicas: 1 # 1개의 복제본으로 시작
  selector:
    matchLabels:
      app: calculator
   template:
     metadata:
       labels:
         app: calculator
       # 프로메테우스가 메트릭을 수집할 수 있도록 annotation 추가
       annotations:
         prometheus.io/scrape: 'true'
         prometheus.io/port: '8000'
         prometheus.io/path: '/metrics'
     spec:
       containers:
       - name: calculator-app
         image: your-dockerhub-username/fastapi-calculator:v1 # 2단계에서 푸시한 이미지
         ports:
         - containerPort: 8000
         # HPA가 동작하기 위해 반드시 필요!
         resources:
           requests:
             cpu: "200m" # 0.2 CPU Core
             memory: "256Mi"
           limits:
             cpu: "500m" # 0.5 CPU Core
             memory: "512Mi"
 ---
 apiVersion: v1
 kind: Service
 metadata:
   name: calculator-service
 spec:
   type: NodePort # NodePort 타입으로 서비스 노출
   selector:
     app: calculator
   ports:
     - protocol: TCP
       port: 8000       # 서비스 내부 포트
       targetPort: 8000 # 파드 포트
       # nodePort: 30100 # 특정 포트 지정 가능 (선택사항)
 ---
 apiVersion: networking.k8s.io/v1
 kind: Ingress
 metadata:
   name: calculator-ingress
 spec:
   ingressClassName: nginx # 사용할 Ingress 클래스 이름
   rules:
   - host: "calculator.example.com" # 사용할 도메인  /etc/hosts 파일  Node의 아이피에 대한 도메인 calculator.example.com 추가해야됨 
     http:
       paths:
       - path: /
         pathType: Prefix
         backend:
           service:
             name: calculator-service
             port:
               number: 8000
```
  > 중요: Ingress를 사용하려면 클러스터에 Nginx Ingress Controller와 같은 Ingress Controller가 미리 설치되어 있어야 합니다.

  이제 이 YAML 파일을 클러스터에 적용합니다.
```
kubectl apply -f calculator-app.yaml
```

```

#예상결과

```

  테스트를 하는 장비의 /etc/hosts파일에  Node의 아이피에 대한 도메인 calculator.example.com 추가합니다

  4단계: JMeter 설치 및 성능 테스트 계획 수립

  JMeter는 보통 로컬 PC에 설치하여 원격 서버(여기서는 쿠버네티스 Ingress)에 부하를 줍니다.

   1. JMeter 설치:
       * Java 8 이상이 설치되어 있는지 확인합니다.
       * JMeter 공식 사이트 (https://jmeter.apache.org/download_jmeter.cgi)에서 최신 버전의 Binaries (zip 또는 tgz)를 다운로드하고 압축을 해제합니다.
       * 압축 해제한 폴더의 bin 디렉토리로 이동하여 jmeter.bat(Windows) 또는 jmeter.sh(Mac/Linux)를 실행하면 GUI가 나타납니다.

   2. 테스트 계획(Test Plan) 수립:
       * Test Plan 우클릭 -> Add -> Threads (Users) -> Thread Group
           * Number of Threads (users): 50 (동시 접속자 수)
           * Ramp-up period (seconds): 10 (10초에 걸쳐 50명이 접속)
           * Loop Count: Forever (테스트를 수동으로 중지할 때까지 계속)
       * Thread Group 우클릭 -> Add -> Sampler -> HTTP Request (덧셈 테스트용)
           * Server Name or IP: calculator.example.com (Ingress에 설정한 호스트)
           * Path: /add
           * Parameters 섹션에서 Add 버튼 클릭:
               * Name: a, Value: 10
               * Name: b, Value: 20
       * 위 HTTP Request를 복사(Duplicate)하여 Path와 파라미터를 /subtract, /multiply, /divide 용으로 각각 만듭니다.
       * Thread Group 우클릭 -> Add -> Listener -> Summary Report (전체 통계 확인용)
       * Thread Group 우클릭 -> Add -> Listener -> View Results Tree (개별 요청/응답 확인용)
       * 이 Test Plan을 CalculatorTest.jmx 와 같은 이름으로 저장합니다.

  6단계: Horizontal Pod Autoscaler (HPA) 설정

  이제 파드의 리소스 사용량에 따라 자동으로 파드 개수를 조절하는 HPA를 설정합니다.

  > 중요: HPA가 CPU/메모리 메트릭을 사용하려면 클러스터에 Metrics Server가 반드시 설치되어 있어야 합니다.
```
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```

```
vi hpa.yaml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: calculator-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: calculator-deployment # 타겟 디플로이먼트
  minReplicas: 1  # 최소 복제본 수
  maxReplicas: 10 # 최대 복제본 수
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70 # CPU 사용률 70%
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80 # 메모리 사용률 80%
```
  YAML 파일을 적용합니다.
```  
kubectl apply -f hpa.yaml
```
  이제 다시 JMeter로 부하를 주면, kubectl get hpa 명령어로 HPA의 상태를 확인했을 때 TARGETS가 70% 또는 80%에 가까워지면서 REPLICAS 수가 3에서 4, 5, ... 로 자동으로 늘어나는 것을 볼 수 있습니다.

  7단계: Alertmanager를 이용한 알림 설정

  kube-prometheus-stack의 Alertmanager를 설정하여 슬랙이나 이메일로 알림을 보냅니다.

   1. PrometheusRule 생성: 어떤 조건에 알림을 보낼지 정의하는 규칙을 만듭니다.
```
vi alert-rules.yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: calculator-alert-rules
  namespace: monitoring # monitoring 네임스페이스에 생성
  labels:
    # 이 레이블이 있어야 kube-prometheus-stack이 규칙을 자동으로 로드합니다.
    release: prometheus 
spec:
  groups:
  - name: calculator-app-alerts
    rules:
    - alert: HighCpuUsage
      expr: >
        (sum(rate(container_cpu_usage_seconds_total{pod=~"calculator-deployment-.*"}[5m])) by (pod) / 
        sum(kube_pod_container_resource_limits{resource="cpu", pod=~"calculator-deployment-.*"} > 0) by (pod)) * 100 > 70
      for: 1m
      labels:
        severity: warning
      annotations:
        summary: "High CPU Usage on {{ $labels.pod }}"
        description: "{{ $labels.pod }} has been using over 70% of its allocated CPU for the last minute."

```
```
#명령어로 monitoring 네임스페이스에 적용합니다.
kubectl apply -f alert-rules.yaml -n monitoring 
```
   2. Alertmanager 설정 수정: kube-prometheus-stack 설치 시 사용했던 custom-values.yaml 파일을 열어 Alertmanager 설정을 추가/수정합니다.
```
vi custom-values.yaml

# 이 파일은 Alertmanager 설정을 위한 샘플입니다.
# 이 파일의 내용을 복사하여 kube-prometheus-stack 설치 시 사용한
# custom-values.yaml 파일에 병합하거나, 이 파일을 직접 수정하여 사용하세요.

alertmanager:
  config:
    global:
      resolve_timeout: 5m

    route:
      group_by: ['job']
      group_wait: 30s
      group_interval: 5m
      repeat_interval: 12h
      # 기본 리시버를 'email-notifications'으로 변경
      receiver: 'email-notifications' 
      routes:
      # severity=warning 레이블을 가진 알림은 email-notifications 리시버로 보냅니다.
      - match:
          severity: warning
        receiver: 'email-notifications'

    receivers:
    # --- 이메일 설정 --- 
    # 중요! 아래의 모든 placeholder 값 (your-email@..., smtp..., your-app-password)을 
    # 자신의 실제 이메일/SMTP 정보로 수정해야 합니다.
    - name: 'email-notifications'
      email_configs:
      - to: 'admin-team@example.com' # 알림을 받을 목적지 이메일 주소
        from: 'alertmanager@your-cluster.com' # 보내는 사람으로 표시될 이메일 주소
        # SMTP 서버 설정 (예: Gmail, 사내 메일 서버 등)
        smarthost: 'smtp.gmail.com:587'
        auth_username: 'your-account@gmail.com' # SMTP 로그인 계정
        auth_identity: 'your-account@gmail.com' # 보통 auth_username과 동일
        # SMTP 비밀번호. Gmail의 경우, 일반 비밀번호가 아닌 '앱 비밀번호'를 생성하여 사용해야 합니다.
        auth_password: 'your-gmail-app-password' 
        send_resolved: true
        headers:
          subject: '[{{ .Status | toUpper }}] {{ .CommonLabels.alertname }} for {{ .CommonLabels.job }}'
        html: '{{ template "email.default.html" . }}'
```
  1. Google 계정 설정 (Gmail SMTP 사용을 위한 필수 단계)

  Gmail SMTP를 사용하려면 Google 계정에서 몇 가지 설정을 해야 합니다.

   1. 2단계 인증 활성화:
       * Google 계정 보안을 강화하고 앱 비밀번호를 생성하기 위해 2단계 인증이 활성화되어 있어야 합니다.
       * Google 계정 관리 페이지로 이동: myaccount.google.com (https://myaccount.google.com/)
       * 왼쪽 메뉴에서 보안을 클릭합니다.
       * Google에 로그인하는 방법 섹션에서 2단계 인증을 찾아 활성화합니다. (이미 활성화되어 있다면 이 단계는 건너뜁니다.)

   2. 앱 비밀번호 생성:
       * 2단계 인증이 활성화된 상태에서만 앱 비밀번호를 생성할 수 있습니다.
       * 보안 페이지에서 Google에 로그인하는 방법 섹션으로 다시 이동합니다.
       * 앱 비밀번호를 클릭합니다.
       * Google 계정 비밀번호를 다시 입력하여 본인임을 확인합니다.
       * 앱 선택 드롭다운에서 메일을 선택합니다.
       * 기기 선택 드롭다운에서 기타 (맞춤 이름)을 선택하고, DevOps Email과 같이 식별 가능한 이름을

       * 생성 버튼을 클릭합니다.
       * 화면에 16자리 앱 비밀번호가 생성되어 표시됩니다. 이 비밀번호를 잘 기록해 두십시오. (다시 볼 수
         없으므로, 지금 복사해 두는 것이 좋습니다.) 이 비밀번호가 DevOps 스크립트에서 Gmail 계정의 비밀번호
         대신 사용될 것입니다.

  8단계: 쿠버네티스 노드(Node) 추가 및 삭제

  노드 관리는 사용 중인 클라우드 제공자(GCP, AWS, Azure 등)나 환경에 따라 방법이 다릅니다.

   * 노드 추가:
       * 클라우드 환경 (GKE, EKS, AKS 등): 보통 관리형 노드 그룹(Managed Node Group)의 '원하는 노드 수(Desired size)'를 늘리는 방식으로 간단하게 추가합니다.
           * (예: GKE) gcloud container clusters resize [CLUSTER_NAME] --node-pool [POOL_NAME] --num-nodes [NEW_NODE_COUNT]
       * 온프레미스/직접 구성: 새로운 머신을 준비하고, kubeadm join과 같은 명령어를 사용하여 기존 클러스터에 수동으로 추가해야 합니다.

   * 노드 삭제:
      중요!: 노드를 그냥 종료하면 해당 노드에서 실행 중이던 애플리케이션이 갑자기 중단될 수 있습니다. 반드시 아래 절차를 따릅니다.

       1. 노드 스케줄링 방지 (Cordon): 더 이상 새로운 파드가 해당 노드에 할당되지 않도록 막습니다.
```
   1.kubectl cordon <node-name>
```
       2. 기존 파드 이전 (Drain): 해당 노드에서 실행 중인 모든 파드를 다른 노드로 안전하게 이동시킵니다.
```
# DaemonSet으로 실행되는 파드는 무시하고 진행
kubectl drain <node-name> --ignore-daemonsets
```
       3. 노드 제거:
           * 클라우드 환경: 노드 그룹의 '원하는 노드 수'를 줄이면 클라우드 제공자가 알아서 노드를 종료하고 클러스터에서 제거합니다.
           * 온프레미스/직접 구성: 노드 머신을 종료한 뒤, 마스터 노드에서 아래 명령어로 클러스터에서 해당 노드 정보를 삭제합니다.
```
kubectl delete node <node-name>
```
